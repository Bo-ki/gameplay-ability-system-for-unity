## 2. 判定词典

- **静态符合**：已检查的源码路径与规则一致；不等于动态验证或全面无缺陷
- **受限符合**：在当前 profile、单 World/单场景等前提下符合，需明列前提
- **目标缺口**：与目标规范之间存在差距，但可能已在阶段范围中明确延期；不等于现有样例必崩溃
- **确认偏差**：源码可直接证明与适用规则或合同不一致，附触发条件
- **待验证**：需编译、运行、Profiler、AOT、故障注入或未公开证据才能判定
- **不适用**：该模块不承担对应职责。例如 Editor 的托管导表不能因未 Burst 就判 Runtime Core 违规

P1/P2 是本报告建议的处理优先级，不替换已有任务树的授权或发布门槛。不用虚构百分比总分；模块检查项数量不同，不能平均成“ECS 合规率”。

## 3. 每份模块报告的检查维度

1. 权威 owner、读写者、World/Session/Battle 隔离和 stable identity
2. Tick/Group、调度依赖、early-out JobHandle、主线程 fence 与 phase fence 区别
3. Component/Buffer/Blob/NativeContainer/cleanup 的选择与生命周期
4. Structural change 是否走正确 playback；数据写是否被错误包装为结构变化
5. allocator、scratch 可用期、持久数据、销毁和 drain
6. deterministic order、same-tick bounded program、下一 Tick reaction
7. managed boundary、表现/诊断是否反向驱动 simulation
8. capacity/scale、Burst/JIT/AOT、性能归因和证据可复现性

不要求每个模块都使用所有 API；要求适用的规则有依据，不适用的规则有边界解释。

## 4. 版本与动态证据边界

仓库文档记录 Unity 6000.3.14f1、Entities 1.4.6、Physics 1.4.6、Entities Graphics 1.4.19、Burst 1.8.29、Collections 2.6.6、Mathematics 1.3.3。实际依赖以该提交的 manifest/lock/版本文件为准。本轮没有访问开发机 PackageCache，也未证明所存官方原件与本机逐字节相等。

历史“11/11、5/5、Player exit 0”等均只能视为对应历史范围的仓库记录，不作为本轮执行结果。代码包含测试也不等于测试已运行。测试缺口与证据未上传分别记录。

## 5. 覆盖口径

本轮按逻辑职责划分 M01–M24，不把每个子目录都机械视为独立产品模块。索引提供目录映射，模块报告分别列实际读取/抽样范围。跨模块调用可交叉引用，但权威问题只在一个主报告详细说明。

第一方实现、配置生成、编辑器、Demo、表现、通用工具、测试、工程依赖与文档治理均有归属。第三方插件内部实现、二进制、Excel 二进制内容、构建产物和历史资料不伪称逐行完成审计；它们作为依赖、输入或证据边界检查。模块覆盖不等于全仓每一行都已经验证。

## 6. 交付与后续使用

本目录是审查证据，不是替代目标态、事实或任务树的新权威规范。不修改业务代码，不替项目 owner 自动扩大支持面。确认后的偏差应按 [ODF-03/04/05 流程](https://github.com/Bo-ki/gameplay-ability-system-for-unity/blob/61daa507e52e823ff42a8cb8c8ec91716c7e80e7/%E6%96%B9%E6%A1%88%E8%AE%A8%E8%AE%BA/UnityDOTS%E5%AE%98%E6%96%B9%E6%96%87%E6%A1%A3%E5%8F%82%E8%80%83/%E4%B8%BB%E9%A2%98/21-%E5%AE%98%E6%96%B9%E6%96%87%E6%A1%A3%E8%A6%86%E7%9B%96%E4%B8%8E%E6%B5%81%E7%A8%8B%E9%97%AD%E7%8E%AF.md)分别反哺设计、事实和任务；本轮仅提出反哺目标，不擅自重写它们。
