# 规范手册

本文件是 EX-GAS 2.0 迭代讨论的唯一规范入口，合并原分散在各目录的 7 个独立规范文件。

## 1. 文档体系结构

### 1.1 目录职责

| 目录 | 职责 | 不写什么 |
|---|---|---|
| `00-当前架构事实/` | 当前代码事实、问题诊断、合规缺陷 | 不写目标态设想和任务状态 |
| `01-目标态架构共识/` | 目标态 Spec、契约、历史方案定位 | 不记录实现流水 |
| `02-主线任务树/` | 任务看板、路线原则、可领取叶子任务 | 不重新定义目标态 |
| `04-当前进度状态/` | 跨轮接力快照、当前窗口 | 不沉淀长期事实 |
| `历史方案参考/` | 方案1-15 原始设计素材 | 不代表当前架构事实 |

### 1.2 文档类型

- **README.md** = 目录导航 + 聚合看板（唯一入口，不设独立的 `_index.md`）
- **事实文档** = 已对照代码/验证成立的当前事实
- **ISSUE-NNN.md** = 单个核心问题的完整诊断
- **Spec 文档** = 目标态设计规范
- **叶子任务** = Agent 可直接领取的执行单元

### 1.3 读者路径

简化为两级导航：
- 根 README → 各子目录 README → 具体内容
- 不允许出现 README → README → _index → 内容 的四层链路

## 2. 核心问题诊断（原 维护规范.md）

### 2.1 问题生命周期

```
Active → Monitoring → Resolved → Archived
```

| 状态 | 含义 |
|---|---|
| Active | 当前影响主线设计或实现 |
| Monitoring | 有修复但需验证观察 |
| Resolved | 满足退出条件，保留一轮复核 |
| Archived | 从看板移除，移入 `_归档/` |

### 2.2 ISSUE 模板（必填5节）

```markdown
# ISSUE-NNN 短标题

## 状态
| 状态 | 严重度 | 最近复核 | 所属层 |
|---|---|---|---|

## 问题陈述
一句话说明问题本质。

## 当前证据
代码路径+行号、profile、异常栈或验证记录。

## 目标态入口
指向具体 Spec 文档。

## 退出条件
问题怎样才算解决。
```

### 2.3 证据等级

| 等级 | 可进入诊断 | 说明 |
|---|---|---|
| A | 是 | 当前代码行号 + profile/验证结果 |
| B | 谨慎 | 用户反馈 + 可复现路径，缺行号或验证；必须标注待补 |

历史方案中的旧诊断不能作为当前事实证据。

### 2.4 合规缺陷生命周期

合规缺陷是**当前问题清单**，不是历史记录：
- **Fixed** → 从活跃文件直接删除
- **Improved** → 重写为当前状态，不留"原为…现已…"的历史叙述
- 活跃文件缺陷数只减不增

## 3. 目标态 Spec 规范（原 Spec规范.md）

### 3.1 Spec 必备结构

每个 Spec 至少覆盖：目的、范围、非目标、术语、架构视图、核心契约、数据所有权、SystemGroup/Phase 顺序、禁止方向、验收方式、关联任务、关联 ADR/方案来源。

### 3.2 "Spec" 三重含义

| 术语 | 含义 | 语境 |
|---|---|---|
| Spec 文档 | 设计规范文档 | 文件名：`03-RuntimeCore管线Spec.md` |
| 运行时 Spec 数据 | GE 施加时的规格数据 | 代码：`GEEffectSpecBuffer` |
| Spec 阶段 | 管线中解析 Spec 的 phase | 架构：`GASSpecEvaluationSystemGroup` |

### 3.3 Unity Entities 校准

Runtime Core Spec 必须说明：SystemGroup 对应、ISystem/Job 方式、ECB 边界、DynamicBuffer 生命周期、Enableable 策略、Blob/Baker 入口、Query filter、Profiler/Journaling、API 选型及拒绝理由。

缺少上述落点的 Spec 只能作为概念草稿，不能作为实现主依据。

## 4. 任务树规范（原 3 个独立文件）

### 4.1 规划 Agent：编写叶子任务

核心原则：**规划 Agent 承担上下文整合成本，执行 Agent 只读一个 .md 文件。**

叶子任务必备字段：`本轮目标`、`非目标`、`目标态约束摘要`、`当前事实约束`、`适用规则摘要`（中文，非裸编号）、`执行细则`（DO/DON'T）、`当前进展`、`验收标准`、`测试链路`。

### 4.2 执行 Agent：领取和交还

1. 只能领取状态为 `就绪`/`进行中` 的叶子节点
2. 只读叶子文件本身——关键约束已内联
3. 领取前自检 5 项（本轮目标、执行细则、规则摘要、当前进展、验收标准），任一不满足则退回
4. 行动报告不等待批准，输出后直接执行

### 4.3 状态流

```
候选 → 就绪 → 进行中 → 已完成 → 已归档
         ↓        ↓
       阻塞 ←─── 阻塞
```

## 5. Agent 行动报告规范（精简）

### 5.1 触发时机

```
任务领取 → 读取上下文 → 行动报告 → 直接执行（不等待批准）
```

### 5.2 Tier 1 必填字段

当前领取任务、所属分支、已读取上下文、当前理解（目标/非目标）、执行边界、行动计划（3-7条）、遵守规范、验收方式、风险/假设。

### 5.3 Tier 2（Runtime Core/Debugger/Luban/Demo 任务额外必填）

API 选型（候选、选择、拒绝理由、健康指标）、官方文档覆盖检查（相关主题、ODF 规则、PackageCache 证据）。

### 5.4 禁止

- 不把行动报告写成请求批准
- 不伪造"已获取上下文"
- Runtime Core 任务必须说明 API 选型理由
- 纯文档治理任务不填 Tier 2/3

## 6. 迭代摘要反哺流程（精简）

### 6.1 两阶段模型

```
Agent 执行业务 → 04 迭代摘要捕获一手信号 → 晋升到长期 owner（00/01/02）
```

### 6.2 反哺路由

| 发现类型 | 目标 owner |
|---|---|
| 代码事实、性能数据、异常栈 | `00-当前架构事实/` |
| 系统性问题 | `00-当前架构事实/` ISSUE |
| 目标设计错误/缺口 | `01-目标态架构共识/` |
| 官方文档新结论 | `UnityDOTS官方文档参考/` |
| 任务拆分变化 | `02-主线任务树/` |
| 验证结果 | `04-当前进度状态/最近验证摘要.md` |

### 6.3 反哺完成标准

已写入对应长期 owner + 有可追溯证据 + 当前窗口能指导下一轮。

### 6.4 严重问题处理

发现严重问题 → 先写入迭代摘要保留原始上下文 → 判断是否满足核心问题标准 → 更新 00/01/02 → 更新当前窗口。

## 7. 命名与格式约定

- 目录用数字前缀排序：`00-`、`01-`、`02-`、`04-`
- 任务名用职责路径拼接：`主线 - 支线 - 叶子`
- Spec 文档：`NN-职责描述Spec.md`
- ISSUE 文档：`ISSUE-NNN-短标题.md`
- 日期格式：`YYYY-MM-DD`

---

## 8. 禁止事项汇总

1. 禁止历史方案旧诊断当作当前事实
2. 禁止没有代码/验证证据标 P0
3. 禁止同一问题拆成多个重复 ISSUE
4. 禁止只更新 `04` 而不更新长期 owner
5. 禁止把目标态设计全文写进 `04`
6. 禁止把 `FedBack` 当作"已想过"的标记——必须有实际文档变更
7. 禁止 Runtime Core 任务行动报告不说明 DOTS API 选型理由
8. 禁止文档治理任务填写 Tier 2/Tier 3 字段
9. 禁止让 `迭代摘要.md` 超过 500 行不滚动清理
