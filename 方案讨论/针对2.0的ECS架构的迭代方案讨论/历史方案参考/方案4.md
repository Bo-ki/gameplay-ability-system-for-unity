# EX-GAS 2.0 深度架构分析与 ECS 原生重构方案

## 瘦身口径

> 已移除基于 2.0 旧状态的开头问题诊断和明显过时的旧状态对比；保留原始方案中仍可借鉴的设计章节、代码块、图示和实施思路。当前分支事实以 `../00-当前架构事实/README.md` 为准；当前任务路线以 `../02-主线任务树/README.md` 为准；目标态吸收关系以 `../01-目标态架构共识/README.md` 及各 Spec 的 `历史方案定位` 为准。

## 二、重构核心原则

```
原则 1: 数据全部在 Entity 上，消除 OOP Controller 层
原则 2: Tag 改用 DynamicBuffer，消除 NativeArray 手动管理
原则 3: Ability Logic 改用 unmanaged ISystem + 注册表，打通 Burst 路径
原则 4: 每个 System 用自己的 ECB，消除全局 EntityHelper 状态
原则 5: Modifier 改用 DynamicBuffer，属性计算全 Burst 化
原则 6: 消除 _bindingAsc 字典，用 EnabledComponent 做状态标记
```

## 三、各子系统重构方案

### 3.1 Tag 系统：`NativeArray<int>` → `DynamicBuffer`

```csharp
// 当前：NativeArray 存在 IComponentData 中，需要手动 Dispose
public struct CAbilityAssetTags : IComponentData {
    public NativeArray<int> tags; // Persistent allocator，手动管理
}
```

**重构方案：**
```csharp
// ✅ 重构后：用 DynamicBuffer，ECS 自动管理内存，Burst 友好
[InternalBufferCapacity(8)] // 内联容量，避免堆分配
public struct BTagElement : IBufferElementData {
    public int TagId;
}

// 区分固定Tag和临时Tag的方式：用两个不同的 Buffer 类型
[InternalBufferCapacity(8)]
public struct BFixedTagElement : IBufferElementData { public int TagId; }

[InternalBufferCapacity(16)]
public struct BTemporaryTagElement : IBufferElementData {
    public int TagId;
    public Entity SourceAbility; // 临时Tag的来源，用于自动清理
}
```

**合理性说明：**
- `DynamicBuffer` 由 ECS 的 `ChunkAllocator` 管理，无需手动 Dispose
- `[InternalBufferCapacity(8)]` 让小数量 Tag 直接内联在 Chunk 中，零堆分配
- Buffer 可以在 Burst Job 中安全读写
- Tag 查询变成纯数据遍历，可以 `[BurstCompile]`

**对应的 Tag 查询 System（完全 Burst 化）：**
```csharp
[BurstCompile]
public partial struct SCheckTagRequirement : ISystem {
    [BurstCompile]
    public void OnUpdate(ref SystemState state) {
        foreach (var (fixedTags, tempTags, req, entity) in
            SystemAPI.Query<
                DynamicBuffer<BFixedTagElement>,
                DynamicBuffer<BTemporaryTagElement>,
                RefRO<CTagRequirement>>()
            .WithEntityAccess()) {

            bool met = CheckRequirement(fixedTags, tempTags, req.ValueRO);
            // 直接在 Burst Job 中完成，无 managed 访问
        }
    }

    [BurstCompile]
    static bool CheckRequirement(
        DynamicBuffer<BFixedTagElement> fixed_,
        DynamicBuffer<BTemporaryTagElement> temp,
        in CTagRequirement req) {
        // 纯值类型操作，完全 Burst 化
        for (int i = 0; i < req.RequiredAll.Length; i++) {
            if (!HasTagInBuffers(fixed_, temp, req.RequiredAll[i])) return false;
        }
        return true;
    }
}
```

### 3.2 Ability Logic：managed class → unmanaged 注册表模式

这是最核心的重构，也是打通 Burst 路径的关键。

```csharp
// 当前：AbilityLogicBase 是 managed class，通过 MCAbilityLogic 挂载
// 导致所有 Ability System 无法 Burst
public abstract class AbilityLogicBase { ... }
public class MCAbilityLogic : IComponentData { public AbilityLogicBase Logic; }
```

**重构方案：函数指针注册表 + unmanaged 数据组件**

```csharp
// ✅ 重构后：用函数指针 + 静态注册表

// 1. Ability 的纯数据组件（unmanaged，Burst 友好）
public struct CAbilityRuntimeData : IComponentData {
    public int Code;
    public int Level;
    public Entity Owner;
    public int ProcessorTypeId; // 指向注册表中的处理器类型
}

// 2. Ability 参数用 DynamicBuffer 存储（替代 XParam managed class）
[InternalBufferCapacity(4)]
public struct BAbilityParamElement : IBufferElementData {
    public int Key;
    public float FloatValue;
    public int IntValue;
    public Entity EntityValue;
}

// 3. 函数指针注册表（静态，Burst 可访问）
public static class AbilityProcessorRegistry {
    // 用 FunctionPointer<T> 存储 Burst 编译的函数指针
    public struct ProcessorEntry {
        public FunctionPointer<OnActivateDelegate> OnActivate;
        public FunctionPointer<OnTickDelegate> OnTick;
        public FunctionPointer<OnEndDelegate> OnEnd;
        public FunctionPointer<OnCancelDelegate> OnCancel;
    }

    [BurstCompile]
    public delegate void OnActivateDelegate(
        Entity abilityEntity, Entity ownerAsc,
        ref GlobalTimer timer, ref EntityCommandBuffer ecb);

    private static readonly NativeHashMap<int, ProcessorEntry> _registry =
        new NativeHashMap<int, ProcessorEntry>(64, Allocator.Persistent);

    public static void Register(int typeId, ProcessorEntry entry) {
        _registry[typeId] = entry;
    }

    public static bool TryGet(int typeId, out ProcessorEntry entry) {
        return _registry.TryGetValue(typeId, out entry);
    }
}

// 4. 具体 Ability 实现（完全 unmanaged，可 Burst）
[BurstCompile]
public static class FireballAbilityProcessor {
    public static readonly int TypeId = AbilityTypeIds.Fireball;

    [BurstCompile]
    public static void OnActivate(
        Entity abilityEntity, Entity ownerAsc,
        ref GlobalTimer timer, ref EntityCommandBuffer ecb) {
        // 纯 ECS 操作，完全 Burst 化
        ecb.AddComponent(abilityEntity, new CAbilityActive());
        // 创建 GE、添加 Tag 等操作全部通过 ECB
    }

    [BurstCompile]
    public static void OnTick(
        Entity abilityEntity, Entity ownerAsc,
        ref GlobalTimer timer, ref EntityCommandBuffer ecb) { ... }
}

// 5. STryActivateAbility 现在可以完全 Burst 化
[BurstCompile]
public partial struct STryActivateAbility : ISystem {
    [BurstCompile]
    public void OnUpdate(ref SystemState state) {
        var ecb = new EntityCommandBuffer(Allocator.Temp);
        var timer = SystemAPI.GetSingleton<GlobalTimer>();

        foreach (var (_, runtimeData, entity) in
            SystemAPI.Query<RefRO<CAbilityInTryActivate>, RefRO<CAbilityRuntimeData>>()
            .WithEntityAccess()) {

            var result = CheckCanActivate(ref state, entity, runtimeData.ValueRO);
            if (result == AbilityActivationResult.Success) {
                if (AbilityProcessorRegistry.TryGet(runtimeData.ValueRO.ProcessorTypeId, out var proc)) {
                    proc.OnActivate.Invoke(entity, runtimeData.ValueRO.Owner, ref timer, ref ecb);
                }
            }
            ecb.RemoveComponent<CAbilityInTryActivate>(entity);
        }

        ecb.Playback(state.EntityManager);
        ecb.Dispose();
    }
}
```

**合理性说明：**
- 函数指针注册表是 Unity DOTS 官方推荐的 "Burst-compatible polymorphism" 模式
- 每个 Ability 类型的逻辑是静态函数，零 GC 分配
- `STryActivateAbility` 现在可以加 `[BurstCompile]`，性能提升数倍
- 参数通过 `DynamicBuffer<BAbilityParamElement>` 传递，替代 managed `XParam` class

### 3.3 消除 `EntityHelper` 全局 ECB 状态

```csharp
// 当前：全局静态 ECB + 三个字典，线程不安全，GC 压力大
private static EntityCommandBuffer _ecb;
private static Dictionary<(Entity, Type), bool> _pendingComponents = new();
private static List<Action> _deferredSetCommands = new();
```

**重构方案：每个 System 持有自己的 ECB，通过 `EndSimulationEntityCommandBufferSystem` 统一 Playback**

```csharp
// ✅ 重构后：标准 DOTS ECB 模式

// 在 System 中声明 ECB System 引用
public partial struct STryActivateAbility : ISystem {
    private EntityCommandBuffer.ParallelWriter _ecbWriter;

    public void OnCreate(ref SystemState state) {
        // 获取 ECB System 的引用（标准 DOTS 模式）
        state.RequireForUpdate<EndSimulationEntityCommandBufferSystem.Singleton>();
    }

    [BurstCompile]
    public void OnUpdate(ref SystemState state) {
        var ecbSingleton = SystemAPI.GetSingleton<
            EndSimulationEntityCommandBufferSystem.Singleton>();
        var ecb = ecbSingleton.CreateCommandBuffer(state.WorldUnmanaged);

        // 直接使用，无需全局状态
        foreach (var (...) in SystemAPI.Query<...>()) {
            ecb.AddComponent<CAbilityActive>(entity);
            ecb.RemoveComponent<CAbilityInTryActivate>(entity);
        }
        // ECB 由 EndSimulationEntityCommandBufferSystem 自动 Playback
        // 无需手动 Dispose，无需 ExecuteDeferredCommands
    }
}
```

**合理性说明：**
- 这是 Unity DOTS 的标准模式，`EndSimulationEntityCommandBufferSystem` 在帧末统一 Playback
- 完全线程安全（`ParallelWriter` 支持 Job 并行写入）
- 零 GC 分配（无 `List<Action>`，无 `Dictionary<(Entity,Type),object>`）
- 消除了 `_deferredSetCommands` 这个脆弱的延迟执行机制

### 3.4 Modifier 系统：managed `MCModifiers` → `DynamicBuffer`

```csharp
// 当前：MCModifiers 是 managed component（class），存储 EffectModifier[]
// 无法 Burst，无法并行
public class MCModifiers : IComponentData {
    public EffectModifier[] Modifiers; // managed array
}
```

**重构方案：**
```csharp
// ✅ 重构后：DynamicBuffer，完全 Burst 化

[InternalBufferCapacity(4)]
public struct BModifierElement : IBufferElementData {
    public int AttrSetCode;
    public int AttrCode;
    public GEOperation Operation;
    public float Magnitude;
    public int MmcCode; // 0 = 直接使用 Magnitude，非0 = 通过 MMC 计算
}

// 属性计算 System 完全 Burst 化
[BurstCompile]
public partial struct SUpdateAttributeCurrentValue : ISystem {
    [BurstCompile]
    public void OnUpdate(ref SystemState state) {
        // 遍历所有 dirty 的 ASC
        foreach (var (attrSets, geBuffer, entity) in
            SystemAPI.Query<
                DynamicBuffer<BEAttrSet>,
                DynamicBuffer<BGameplayEffect>>()
            .WithAll<CAttributeIsDirty>()
            .WithEntityAccess()) {

            // 重置 CurrentValue = BaseValue
            ResetCurrentValues(attrSets);

            // 遍历所有激活的 GE，应用 Modifier
            foreach (var geRef in geBuffer) {
                if (!state.EntityManager.HasComponent<CEffectActive>(geRef.Effect)) continue;
                var modifiers = state.EntityManager.GetBuffer<BModifierElement>(geRef.Effect);
                ApplyModifiers(attrSets, modifiers);
            }
        }
    }

    [BurstCompile]
    static void ApplyModifiers(
        DynamicBuffer<BEAttrSet> attrSets,
        DynamicBuffer<BModifierElement> modifiers) {
        // 纯值类型操作，完全 Burst 化，可以 SIMD 优化
        for (int i = 0; i < modifiers.Length; i++) {
            ref var mod = ref modifiers.ElementAt(i);
            // 找到对应属性并应用
            ApplySingleModifier(attrSets, mod);
        }
    }
}
```

**合理性说明：**
- `DynamicBuffer<BModifierElement>` 替代 `MCModifiers`（managed class），打通 Burst 路径
- 属性计算是 GAS 中最高频的操作（每帧每个有 GE 的 ASC 都要算），Burst 化收益最大
- `[InternalBufferCapacity(4)]` 对于大多数 GE（通常 1-4 个 Modifier）零堆分配

### 3.5 消除 `_bindingAsc` 字典：用 `IComponentData` 存储所有需要的数据

```csharp
// 当前：静态字典，ECS 系统需要反查 OOP 对象
private static readonly Dictionary<Entity, AbilitySystemCell> _bindingAsc = new();
```

**根本原因**：ECS System 内部需要访问 `AbilitySystemCell` 的方法（如 `ApplyGameplayEffect`），而这些方法在 OOP 层。

**重构方案：将所有操作下沉到 ECS，消除反查需求**

```csharp
// ✅ 重构后：GE 的 Source/Target 直接存储 Entity，不需要 OOP 对象

// GE 的使用信息（已有，保留）
public struct CEffectInUsage : IComponentData {
    public Entity Source; // Source ASC Entity
    public Entity Target; // Target ASC Entity
    public int Level;
}

// System 直接操作 Entity，不需要 AbilitySystemCell
[BurstCompile]
public partial struct SAddModifiers : ISystem {
    [BurstCompile]
    public void OnUpdate(ref SystemState state) {
        var ecb = new EntityCommandBuffer(Allocator.Temp);

        foreach (var (inUsage, modifiers, geEntity) in
            SystemAPI.Query<RefRO<CEffectInUsage>, DynamicBuffer<BModifierElement>>()
            .WithAll<CEffectInActivate>()
            .WithEntityAccess()) {

            var targetAsc = inUsage.ValueRO.Target;
            // 直接操作 Target Entity，无需 OOP 对象
            ecb.AppendToBuffer(targetAsc, new BActiveModifierRef {
                GeEntity = geEntity
            });
            ecb.AddComponent<CAttributeIsDirty>(targetAsc);
        }

        ecb.Playback(state.EntityManager);
        ecb.Dispose();
    }
}
```

**合理性说明：**
- 真正的 ECS 设计中，所有数据都在 Entity 上，System 只操作 Entity
- 消除 `_bindingAsc` 字典后，GAS 世界内部完全无 managed 状态
- `AbilitySystemCell` 退化为纯粹的**用户侧 Facade**（只在 MonoBehaviour 层使用），不再参与 ECS 内部逻辑

### 3.6 系统组层级扁平化

**当前：4 层嵌套**
```
SGEffect
  └─ SGEffectOperation
       ├─ SGCheckApplyEffect
       │    ├─ SCheckApplicationRequiredTags
       │    ├─ SCheckImmunityTags
       │    └─ SCheckApplyEnd
       ├─ SGApplyEffect
       │    ├─ SPlayCueOnApply
       │    ├─ SRemoveEffectWithTags
       │    └─ SApplyEnd
       ...
```

**重构方案：用 `[UpdateBefore]`/`[UpdateAfter]` 替代嵌套 SystemGroup**

```csharp
// ✅ 重构后：扁平化，用 Order Attribute 控制顺序

[UpdateInGroup(typeof(SGEffect))]
[UpdateBefore(typeof(SCheckImmunityTags))]
public partial struct SCheckApplicationRequiredTags : ISystem { ... }

[UpdateInGroup(typeof(SGEffect))]
[UpdateAfter(typeof(SCheckApplicationRequiredTags))]
[UpdateBefore(typeof(SApplyEffect))]
public partial struct SCheckImmunityTags : ISystem { ... }

[UpdateInGroup(typeof(SGEffect))]
[UpdateAfter(typeof(SCheckImmunityTags))]
public partial struct SApplyEffect : ISystem { ... }
```

**合理性说明：**
- 减少 SystemGroup 层级，降低调度开销
- `[UpdateBefore/After]` 是 Unity ECS 的标准顺序控制机制
- 代码结构更清晰，每个 System 的依赖关系一目了然

## 五、重构合理性总结

| 问题 | 当前实现 | 重构方案 | 业务收益 |
|---|---|---|---|
| Tag 存储 | `NativeArray<int>` in IComponentData，手动 Dispose | `DynamicBuffer<BTagElement>`，自动管理 | 消除内存泄漏风险，Tag 查询可 Burst |
| Ability Logic | `AbilityLogicBase` managed class | 函数指针注册表 + unmanaged 数据 | `STryActivateAbility` 可 Burst，性能数倍提升 |
| ECB 管理 | 全局静态 ECB + `List<Action>` | 每 System 独立 ECB，EndSim 统一 Playback | 线程安全，零 GC，消除延迟执行 bug |
| Modifier 存储 | `MCModifiers` managed class | `DynamicBuffer<BModifierElement>` | 属性计算全 Burst，支持 Job 并行 |
| OOP 反查 | `Dictionary<Entity, AbilitySystemCell>` | 消除，所有操作下沉到 ECS | 消除全局状态，ECS 内部零 managed |
| 系统组层级 | 4 层嵌套 SystemGroup | 扁平化 + Order Attribute | 降低调度开销，结构清晰 |
| Ability 查找 | O(n) 遍历 BAbility buffer | `NativeHashMap<int, Entity>` 作为 Singleton | O(1) 查找，高频操作性能提升 |

**最核心的一句话**：当前架构的 ECS 化是**形式上的**（数据在 Entity 上），但**控制流仍然是 OOP 的**（Controller 驱动 Entity）。真正的 ECS 原生设计应该是**数据在 Entity 上，控制流在 System 中，OOP 层只做最薄的 Facade**。`AbilityLogicBase` 这个 managed class 是整个架构中最大的性能天花板，将其替换为函数指针注册表是最高优先级的重构项。
