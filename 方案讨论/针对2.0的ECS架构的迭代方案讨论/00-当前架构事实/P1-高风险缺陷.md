# P1 高风险缺陷

> 最近审查：2026-06-02 | 事实源：当前代码

P1 记录不会立即阻断主链，但会持续扩大维护成本、性能风险或目标态偏差的问题。

## P1-A：5 段物理主链与 8 个逻辑 phase contract 并存

当前真实物理执行域是 5 个 group：

1. `GASFramePrepareSystemGroup`
2. `GASCommandResolveSystemGroup`
3. `GASCoreSimulationSystemGroup`
4. `GASStructuralCommitSystemGroup`
5. `GASBoundaryProjectionSystemGroup`

`GASSystemScheduleContract` 内还保留 8 个逻辑 phase 枚举：

- FramePrepare
- CommandIngest
- SpecEvaluation
- ActiveEffectLifecycle
- DeltaApply
- TypedFactProjection
- StructuralPlayback
- ObservationProjection

这不是错误，但文档和任务必须区分“物理 group”与“逻辑 phase”。当前代码不是旧 8 个 physical group，也不是旧 `GasStructuralPlaybackSystemGroup`。

## P1-B：部分系统类型存在但未进入主注册表

当前存在但未直接注册进 `GASSystemScheduleContract` 主表的类型包括：

- `GEEffectCommandIngestSystem`
- `GameplayFactEventBridgeSystem`
- `GEInstantEffectCueRequestProjectionSystem`
- `AttributeChangeEventProjectionSystem`
- `GASManagerInputSystem : SystemBase`

这些类型可能是迁移期残留或待启用能力。后续启用前必须说明与 generated systems、`GameplayFactProjectionSystem`、BoundaryProjection 的职责关系，避免重复 projection 或重复消费。

## P1-C：typed fact 与 legacy EventBus 并存

当前 positive fact：

1. `GameplayFactProjectionSystem` 已能把 delta 投影为 `GameplayEventBuffer` typed facts。
2. `PresentationOutboxProjectionSystem` 与 `ReplayLogSystem` 位于 BoundaryProjection。
3. `AutoChessExecuteDamageCalculationSystem` 会写 typed fact，并通过 EventBus writer 兼容旧 event。

风险：

- legacy EventBus 仍作为 singleton buffer owner 存在。
- 部分 gameplay / presentation / replay 路径仍依赖 legacy event。
- 如果业务 reaction 继续从 EventBus 扫描，就会把 Observation 重新拉回 CoreSimulation。

## P1-D：Cue 仍是 managed presentation bridge

当前 `CueManagedInstanceComponent` / `GameplayCueBase` 等 managed cue 路径位于 BoundaryProjection。作为表现桥接可接受，但它不能被当作 Burst gameplay core。

风险重点不是“Cue 必须立刻全 Burst”，而是：

1. Cue 不应反馈 CoreSimulation。
2. Cue 的 managed cost 要在 Observation/Presentation 维度单独报告。
3. Gameplay fact / replay 不能依赖 cue managed instance 作为权威事实。

## P1-E：ConfigRegistry 与 prototype cache 是全局 managed 状态

当前仍有：

- `ConfigRegistryDiagnostics` 静态 `List` / `HashSet`
- `GameplayEffectConfigRegistry` 静态 `Dictionary<int, Entity>`
- `GameplayEffectConfigRegistry` 静态 `Dictionary<int, BlobAssetReference<GEStaticDefinitionBlob>>`
- `TagHelper` 静态 `Dictionary`
- `CueHelper` / `TargetCatcherHelper` 静态反射映射

这些可以是初始化、Editor、authoring、presentation 路径，但不应进入 runtime hot path。后续需要用 catalog blob / generated lookup / explicit owner 替代 hot path 查询。

## P1-F：Definition/Baking contract 未证明 Unity Baker 集成

`GASGeneratedDefinitionBakingPlan`、`BakeContract`、`BakePipeline`、`RuntimeIntegrationPlan` 仍是 contract/plan 层。当前实际代码树中没有生成到 Runtime/AutoChess 的 `Baker<T>` 类，也没有 `BlobAssetStore` 生命周期 owner。

这意味着：

1. 不能把 contract 文件当 Baker 完成证据。
2. 当前 catalog blob 接入是 runtime 正向事实，但 baking/sourcegen 链仍需实际产物证明。
3. AutoChess 当前手写 catalog 不能替代 Spec 11 配置驱动验收链。

## P1-G：AutoChess bridge 集中但仍未结构化

`AutoChessGasCoreBridge` 已把 Demo 到 GAS Core 的调用集中起来，这是架构正向变化。但 bridge 内部仍直接创建/销毁 entity、清 buffer、读写 singleton。

后续应把这些操作分类：

| 类别 | 当前可接受度 | 后续方向 |
|---|---|---|
| Runtime 初始化/Shutdown | 可接受 | 保留在 bridge |
| Catalog 安装/卸载 | 可接受但要 owner 化 | 明确 catalog owner entity |
| 战斗单位创建/销毁 | 迁移风险 | 改为 request/command 或 session-owned lifecycle |
| Observation reset/export | 可接受但需隔离成本 | 不计入 CoreSimulation 性能 |
| 热路径 tick 写入 | 高风险 | 进入 command sink / job chain |

## P1-H：SystemAPI.Query 主线程路径仍多

当前 `SystemAPI.Query<...>` 命中包括：

- generated active effect pre-tick
- Cue start/tick/end/destroy
- AutoChess command drive

根据 Unity Entities 机制，`SystemAPI.Query` 是主线程 foreach，并会处理相关 dependency。它适合过渡实现和低频/managed boundary，不适合被默认为 high-scale hot path 答案。

## P1 退出条件

1. 文档统一使用当前 5 段 physical group 名称，并明确 8 phase 只是逻辑 contract。
2. 未注册系统有去留结论：启用、删除或归档。
3. typed fact 与 legacy EventBus 的职责分界清晰，业务 reaction 不再依赖 observation bus。
4. managed registry/helper/cue 路径全部标注为初始化、authoring 或 presentation，不混入 CoreSimulation。
5. AutoChess bridge 的结构变化被纳入明确 owner 或 request/command 模式。
