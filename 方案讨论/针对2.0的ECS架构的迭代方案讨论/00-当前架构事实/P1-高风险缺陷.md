# P1 高风险缺陷

> 最近审查：2026-06-07 | 事实源：当前代码

P1 记录不会立即阻断主链，但会持续扩大维护成本、性能风险或目标态偏差的问题。

## P1 分类边界

本页不再把所有直接 `EntityManager`、managed registry、主线程查询都一律升为 P0。当前分类口径如下：

| 分类 | 判定标准 | 当前处理 |
|---|---|---|
| P0 | 发生在 Runtime Core hot path，且会破坏 frame phase、结构变化边界或高规模确定性 | 必须进入主链修复任务 |
| P1 | 集中在初始化、Boundary、Demo adapter、generated 过渡系统或 managed presentation，但会扩大维护/性能风险 | 需要 owner 化、迁移计划和证据跟踪 |
| P2 | 主要是命名、文档新鲜度、检查流程或任务治理问题 | 作为后续治理建议 |

因此 `AutoChessGasCoreBridge` 这类集中 adapter 内的直接 `EntityManager` 操作属于 P1/P0 交界：初始化、catalog 安装、observation reset 可暂按 P1 管理；如果同类写法进入 `GASCoreSimulationSystemGroup` 热路径，就必须升为 P0。

## P1-I：策划配置能力链路缺失

当前 GAS Center UI Toolkit 已能编辑 Ability / Effect 表行，但默认对象仍是 Excel row、裸 ID 和协议字段，不是策划真正要维护的业务能力包。Ability 页保存 `ID / Name / Desc / Cost / CdEffect / Cd / Tag 列 / AbilityExecution` 并写回 execution 后续 50 个 raw 参数列；Effect 页保存 Duration / Period / Stacking 的 offset raw columns，并直接暴露 `Modifiers`、`GrantedAbility`、TagRequirement 文本协议。

这导致配置链出现两个断层：

1. **Editor 与策划意图断层**：策划想编辑“火球术 / 中毒 DOT / 被动光环”，工具要求编辑多张表和协议字段。
2. **Editor 与 Runtime 语义断层**：Runtime 已消费 `GASDefinitionCatalogBlob`、`AbilityActivationPlanRecord`、`GECommandSeedRecord`、`ResolvedModifierRecord`，Editor 却没有业务包级 Runtime trace preview。

该问题的详细诊断见 [ISSUE-012-策划配置能力缺失](ISSUE-012-策划配置能力缺失.md)。后续不应把“Ability / Effect 页能保存 Excel”写成策划配置能力完成证明。

目标态退出条件：

1. 默认新建对象是 Ability Package / Effect Package，而不是单张 row。
2. 保存前有 Config Graph Validation，能按业务包聚合引用缺失、策略冲突、DOTS carrier 和 SourceGenerator gate。
3. 修改 Ability / GE / Cue / Tag / Attribute 时能输出 Impact Analysis。
4. 保存或发布前能输出 Runtime Trace Preview。
5. Raw Table 仅保留为 Advanced Mode，默认路径不要求手写 raw protocol。

## P1-J：新增能力业务推进链路过长

当前新增一个能力时，策划和程序没有共享的分类门禁。配置型能力、胶水扩展型能力和 Runtime 语义型能力混在同一条“建 row、填 ID、写协议、导出、看 report、跑 demo、找程序”的链路里。

这导致两个问题：

1. 策划无法知道哪些动作是业务必须、哪些应由模板 / SourceGenerator 自动生成、哪些真的需要程序介入。
2. 程序无法快速判断该补 Generated Editor Binding / evaluator / target rule，还是必须改 Runtime Core lane / store / structural policy。

该问题的详细诊断见 [ISSUE-013-新增能力业务推进链路过长](ISSUE-013-新增能力业务推进链路过长.md)。目标态流程见 `../01-目标态架构共识/22-新增能力业务推进流程Spec.md`。

目标态退出条件：

1. 新增能力默认先进入 Ability Addition Workflow 三档分类。
2. Configuration-Only Ability 必须做到程序 0 代码。
3. Generated Glue Extension 只能改 SourceGenerator metadata / pure glue / Editor Binding / validation，不生成 Runtime lifecycle。
4. Runtime Semantic Extension 必须先输出 DOTS Official Review Gate，再改 Runtime Core。
5. Business Package Change Set、Impact Analysis、Runtime Trace Preview、Scenario Validation Evidence 和 Publish Validation Snapshot 成为新增能力发布的默认证据。

## P1 退出条件

1. 文档统一使用当前 5 段 physical group 名称，并明确 8 phase 只是逻辑 contract。
2. 未注册系统有去留结论：启用、删除或归档。
3. typed fact 与 legacy EventBus 的职责分界清晰，业务 reaction 不再依赖 observation bus。
4. managed registry/helper/cue 路径全部标注为初始化、authoring 或 presentation，不混入 CoreSimulation。
5. AutoChess bridge 的结构变化被纳入明确 owner 或 request/command 模式。
6. generated active mutation 的 gather + ASC chunk-local apply contract 保持由 static validation 防回流；command carrier、SourceAttribute snapshot lane、generated delta record carrier 有去留结论或拆分计划。已收口的 ability lifecycle、attribute owner marker、execution output applied、active mutation apply 和 pending AttributeDelta apply 链路继续由 static validation 防回流；已 job 化链路需要补 dependency/order/capacity 证据，并用 static validation 防止 `.gen.cs` 回到未 Burst、random enableable、旧 serial apply 或主线程 proof 形态。
7. 策划配置能力链路退出表行默认路径：业务能力包、配置图校验、影响分析、Runtime trace preview 和发布校验快照成为默认验收口径。
8. 新增能力链路退出“每次都像要程序参与”的状态：配置型能力程序 0 代码，胶水扩展不触碰 Runtime lifecycle，Runtime 语义扩展先通过 DOTS Official Review Gate。

## 后续瘦身事实约束

本轮已删除旧事实源，不做兼容适配。后续任务的事实约束为：
