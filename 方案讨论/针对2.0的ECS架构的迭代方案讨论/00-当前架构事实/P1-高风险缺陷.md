# P1 高风险缺陷

> 最近审查：2026-06-06 | 事实源：当前代码

P1 记录不会立即阻断主链，但会持续扩大维护成本、性能风险或目标态偏差的问题。

## P1 分类边界

本页不再把所有直接 `EntityManager`、managed registry、主线程查询都一律升为 P0。当前分类口径如下：

| 分类 | 判定标准 | 当前处理 |
|---|---|---|
| P0 | 发生在 Runtime Core hot path，且会破坏 frame phase、结构变化边界或高规模确定性 | 必须进入主链修复任务 |
| P1 | 集中在初始化、Boundary、Demo adapter、generated 过渡系统或 managed presentation，但会扩大维护/性能风险 | 需要 owner 化、迁移计划和证据跟踪 |
| P2 | 主要是命名、文档新鲜度、检查流程或任务治理问题 | 作为后续治理建议 |

因此 `AutoChessGasCoreBridge` 这类集中 adapter 内的直接 `EntityManager` 操作属于 P1/P0 交界：初始化、catalog 安装、observation reset 可暂按 P1 管理；如果同类写法进入 `GASCoreSimulationSystemGroup` 热路径，就必须升为 P0。

## 官方规则对照

|---|---|---|

## P1-A：5 段物理主链与 8 个逻辑 phase contract 并存

当前真实物理执行域是 5 个 group：

1. `GASFramePrepareSystemGroup`
2. `GASCommandResolveSystemGroup`
3. `GASCoreSimulationSystemGroup`
4. `GASStructuralCommitSystemGroup`
5. `GASBoundaryProjectionSystemGroup`

`GASSystemScheduleContract` 内还保留 8 个逻辑 phase 枚举：

- FramePrepare
- CommandIngest
- SpecEvaluation
- ActiveEffectLifecycle
- DeltaApply
- TypedFactProjection
- StructuralPlayback
- ObservationProjection

这不是错误，但文档和任务必须区分“物理 group”与“逻辑 phase”。当前代码不是旧 8 个 physical group，也不是旧 `GasStructuralPlaybackSystemGroup`。

## P1-C：typed fact 与 legacy EventBus 并存

当前 positive fact：

1. `GameplayFactProjectionSystem` 已能把 delta 投影为 `GameplayEventBuffer` typed facts。
2. `GameplayFactProjectionSystem` 已改为 scheduled `IJob`，在 lookup writer 中桥接 Attribute/Cue legacy EventBus，不再走主线程 `EventBusHelper.GameplayEventBusWriter`。
3. `PresentationOutboxProjectionSystem` 与 `ReplayLogSystem` 位于 BoundaryProjection。
3. `AutoChessExecuteDamageCalculationSystem` 会写 typed fact，并通过 EventBus writer 兼容旧 event。

风险：

- legacy EventBus 仍作为 singleton buffer owner 存在。
- 部分 gameplay / presentation / replay 路径仍依赖 legacy event。
- 如果业务 reaction 继续从 EventBus 扫描，就会把 Observation 重新拉回 CoreSimulation。

## P1-D：Cue 仍是 managed presentation bridge

当前 `CueManagedInstanceComponent` / `GameplayCueBase` 等 managed cue 路径位于 BoundaryProjection。作为表现桥接可接受，但它不能被当作 Burst gameplay core。

风险重点不是“Cue 必须立刻全 Burst”，而是：

1. Cue 不应反馈 CoreSimulation。
2. Cue 的 managed cost 要在 Observation/Presentation 维度单独报告。
3. Gameplay fact / replay 不能依赖 cue managed instance 作为权威事实。

## P1-G：AutoChess bridge 集中但仍未结构化

`AutoChessGasCoreBridge` 已把 Demo 到 GAS Core 的调用集中起来，这是架构正向变化。但 bridge 内部仍直接创建/销毁 entity、清 buffer、读写 singleton。

后续应把这些操作分类：

| 类别 | 当前可接受度 | 后续方向 |
|---|---|---|
| Runtime 初始化/Shutdown | 可接受 | 保留在 bridge |
| Catalog 安装/卸载 | 可接受但要 owner 化 | 明确 catalog owner entity |
| 战斗单位创建/销毁 | 迁移风险 | 改为 request/command 或 session-owned lifecycle |
| Observation reset/export | 可接受但需隔离成本 | 不计入 CoreSimulation 性能 |
| 热路径 tick 写入 | 高风险 | 进入 command sink / job chain |

## P1-H：SystemAPI.Query 主线程路径已收窄，serial buffer loop 仍多

当前 `Assets/GAS` 内 `SystemAPI.Query<...>` 只命中 Cue start/tick/end/destroy managed boundary：

根据 Unity Entities 机制，`SystemAPI.Query` 是主线程 foreach，并会处理相关 dependency。它适合过渡实现和低频/managed boundary，不适合被默认为 high-scale hot path 答案。

证据锚点：

| 路径 | 代码证据 | 当前分类 |
|---|---|---|
| Cue start/tick/end/destroy | `Assets/GAS/Runtime/System/Cue/CueStartSystem.cs:22`、`CueTickSystem.cs:21`、`CueEndSystem.cs:23`、`CueDestroySystem.cs:23` | Boundary managed path |
| AutoChess command drive | `Assets/AutoChessDemo/Battle/Ecs/AutoChessBattleCommandDriveSystem.cs:52-80`、`:87-236` | 已迁为 scheduled collect/flush jobs |
| AutoChess catalog singleton lookup 使用 `ToEntityArray` | `Assets/AutoChessDemo/Battle/Ecs/AutoChessBattleDefinitionCatalogBuilder.cs:122-141` | 低频初始化，需 owner 化 |

补充事实：

1. generated `GASActiveEffectPreTickSystem` 已改为 scheduled `GEActiveEffectPreTickJob`，不再 `SystemAPI.Query` pre-scan。
2. `AttributeRecalculateSystem` 已删除 `CalculateEntityCount()` + 小规模主线程 fallback，统一走 scheduled `IJobEntity`。
3. `AbilityStateCleanupSystem` 已改为 scheduled `IJobChunk`，旧主线程 cleanup loop 与 `EntityManager` helper 退场。
4. AutoChess command drive / execute calculation 已改为 scheduled job，并由 batchmode x50 验证通过。
5. `ASCCommandBufferResolveSystem`、generated `AbilityCatalogCommitSystem`、generated normalize/spec-build/reduce、generated active pre-tick/remove、stream frame prepare 和 fact projection 已改为 scheduled job。
6. generated `AbilityCatalogCommitSystem` 已从 random-access `ComponentLookup.SetComponentEnabled` 切到 chunk `EnabledMask`；此项不再作为 `EN-03` 风险记录，只保留 static validation 防回流。
7. generated `RuntimeEffectInstant` 的 spec-build / attribute-reduce 已是 `[BurstCompile] IJob`，且 codegen 模板同步；不能再把 instant spec/reduce 写作主线程 proof。
8. `ASCDestroyingComponent` 判定已按 enableable bit 读取；默认 disabled 的正常 ASC 不再被 generated path 当作 destroying。
9. generated active lifecycle 仍有 random-access enableable 残留：`RemovePendingLookup.SetComponentEnabled(owner, false)`、`AbilityCancelRequestLookup.SetComponentEnabled(ability, true)`、`AbilityDestroyOnCleanupLookup.SetComponentEnabled(ability, true)`、`ActiveModifierPresentLookup.SetComponentEnabled(asc, ...)`、`AttributeDirtyLookup.SetComponentEnabled(asc, true)`。这些发生在 scheduled job 中，按 `EN-03` / `CASE-20` 属 P1，后续应改为 owner-local state 或 chunk-local mask。
10. P1 重心从广义 `SystemAPI.Query` 数量转为 generated active mutation `EntityManager` helper、generated active lifecycle random enableable、singleton stream pressure、legacy EventBus writer、static validation 缺口和结构变化证据闭环。

## P1 退出条件

1. 文档统一使用当前 5 段 physical group 名称，并明确 8 phase 只是逻辑 contract。
2. 未注册系统有去留结论：启用、删除或归档。
3. typed fact 与 legacy EventBus 的职责分界清晰，业务 reaction 不再依赖 observation bus。
4. managed registry/helper/cue 路径全部标注为初始化、authoring 或 presentation，不混入 CoreSimulation。
5. AutoChess bridge 的结构变化被纳入明确 owner 或 request/command 模式。
6. generated active mutation 的 serial buffer loop / `EntityManager` helper 有去留结论或 job 化计划；generated active lifecycle random enableable 有 owner-local/chunk-local 收口方案；已 job 化链路需要补 dependency/order/capacity 证据，并用 static validation 防止 `.gen.cs` 回到未 Burst、random enableable 或主线程 proof 形态。
