## 问题陈述

任务树节点如果只写任务名和简短描述，Agent 执行时会重新搜索上下文，容易从局部代码或历史方案示例直接实施，而不是从目标态 Spec 拆解任务。这是此前 Runtime 执行偏差的流程原因之一。

## 当前证据

文档证据：

1. 当前用户已明确目标链路为 `历史方案讨论 -> 目标态架构共识 -> 主线任务树 -> Goal 循环推进`。
2. `02-主线任务树/README.md` 已要求一级、二级、三级节点都必须写清当前问题、目标态参考、历史方案参考、目标 / 非目标、执行范围、验收标准和测试链路。
3. `12-命名规范Spec.md` 已要求任务名采用“主任务线名 - 副任务线名 - 任务名”的职责拼接，不用抽象代号作为主标题。

执行偏差证据：

1. 路线反思指出当前实现吸收了业务闭环、Replay、structured log、Luban 样板，但没有同步兑现 Pure ECS Core 前提：`../../../迭代记录/92-T6-CHESS-AL-RouteReflectionFromPlans12To15.md:51-58`。
2. 流程原因包括性能门槛和 Runtime Core Debugger 建设滞后：`../../../迭代记录/92-T6-CHESS-AL-RouteReflectionFromPlans12To15.md:64-68`。

## 执行路径

```text
任务卡上下文不足
-> Agent 直接读历史方案或局部代码
-> 吸收业务示例但遗漏目标态约束
-> EventBus / instant GE entity / Demo 巨类等实现偏差扩大
-> 再通过 profile 和技术停顿反推架构问题
```

## 影响

1. 目标态 Spec 和执行任务断链，导致同一类偏差反复出现。
2. 每次交接需要重新解释历史方案定位，浪费 Goal 循环上下文。
3. 问题解决后如果不归档，当前事实也会膨胀失真。

## 根因反推

任务树不是普通 TODO list，而是目标态 Spec 的可执行拆解。每个任务节点都必须像 Agent prompt，一次性提供背景、证据、目标态约束、执行范围和验收方式。
