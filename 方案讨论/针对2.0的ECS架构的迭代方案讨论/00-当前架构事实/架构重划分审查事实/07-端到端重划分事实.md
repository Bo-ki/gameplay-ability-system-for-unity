## 本轮端到端事实结论

当前 EX-GAS 已经具备一条可演进的 ECS Runtime 主链，但端到端职责仍没有完全按 Shell / Boundary / Core / Debugger / Definition 分离。最关键的事实不是“是否存在 ISystem”，而是调用方仍在多个位置必须理解 ECS handle、singleton owner、generated lifecycle、NativeContainer owner、capacity 或 observation cost。

| 端到端切片 | 当前代码事实 | DOTS 判定 |
|---|---|---|
| Runtime install / tick | `GASManager.Initialize()` 集中创建 World、system group、全局 singleton 和 Debugger；AutoChess host / ticker 通过 runtime access wrapper 间接获取 World、group 和 job drain | bootstrap owner 已集中，是正向事实；但 RuntimeSession seam 仍未把 World / EntityManager / job drain 从业务 adapter public 语义中彻底隔离 |
| Shell command write | `GASRuntimeShell.TryCreateASCCommandPort(...)` 与 `AbilitySystemBinding.Commands` 已把外部 command 集中到 command port | 写入口方向正确；但同一 Shell facade 仍能创建 read model、解析 singleton、drain jobs 和 bind presentation，capability 未分级 |
| Core command resolve | `ASCCommandBufferResolveSystem` 已使用 `ISystem`、stored query、type handle、enabled mask、scheduled `IJobChunk`、ECB 和 catalog | DOTS API 形态正向；但单个 job interface 过宽，command、ability slot、tag mask、attribute base value 和 fact 写入仍在同一 lane |
| Effect fan-in / frame stream | `GEEffectCommandSpecStream` 删除了 fallback query，`HasRequiredBuffers` 当前只要求 `GEEffectCommandStreamComponent`；EffectCommand / SetByCaller / TypedSimulationFact 当前仍有 singleton carrier；InstantEffectSpec / ActiveEffectMutation / ActiveEffectNextFrameMutation / OwnerLocalInstantNextFrame / AttributeDelta 已是 owner-local current carrier，但 scaleStatus 仍为 MigrationCarrier；ASC command resolve、pending AttributeDelta、hand-written instant reduce 与 execution output modifier apply 已先写 ASC `OwnerLocalGameplayFactBuffer`，再由 `GEEffectCommandSpecStreamPhases` 收集、排序并导出到 Boundary observation / 现有 stream fact export | `BUF-02` / `NAT-03` 判定为迁移 proof；删除 fallback query、收窄 required stream owner、局部 NativeStream 切片、owner-local spec / mutation / delta carrier 或 owner-local fact 扩展切片都不能证明 scale-ready fan-in / fact export 全链路完成 |
| Active effect lifecycle | 手写 Runtime `GASActiveEffectMutationApplySystem` / `GASActiveEffectPreTickSystem` / `GASActiveEffectRemoveSystem` 已从 `RuntimeActiveEffect.gen.cs` 与 manifest lifecycle 输出退出，helper/job 主体位于 `GASActiveEffectRuntime.cs` / `GEActiveEffectLifecycleSystems.cs`；slot SourceAttribute snapshot key 和 capacity estimator 已存在；`ActiveEffectLifecycleOwnerSystems.cs` 当前磁盘缺失 | active effect store 方向正向；但 capacity / spill / lane-specific evidence / x100-x1000、catalog bootstrap owner、manifest/report/file/schedule 对账和 generated lifecycle 防回流未闭合 |
| Definition consumption | generated catalog lookup、activation plan、GE seed、modifier record、magnitude evaluator、TagRequirement evaluator 已是 unmanaged / Blob-oriented pure resolver；Ability/GE all-any-none requirement 当前进入 `GASDefinitionCatalogBlob.Requirements` | 这是 Definition & Generation 的正向保留面；不应与 generated lifecycle system 混为同一完成度 |
| Debugger / evidence | Debugger 记录 RuntimeCore、frame backbone、magnitude source、observation materialization 等 counter；structured export / official diff / validation evidence 已出现 | Debugger 已是 evidence owner；derived export、observation materialization 和 official capture 必须独立计时，不能混入 CoreSimulation 结论 |
| AutoChess adapter | AutoChess Integration/GasCore 已拆出 runtime access wrapper、host、catalog session、observation gateway、lifecycle、ticker、report projector；但 wrapper 内仍代理 Shell 的 World / EntityManager / singleton / job drain capability | Demo adapter 是 Application Shell 验收层；当前是 proof-compatible adapter，不是 Thin Adapter 完成态 |

## 2026-06-08 续轮三次校准

本次端到端审查新增三个事实校准：

1. Shell 消费者口径应分层记录：`codedb_deps` 当前识别 `AutoChessGasRuntimeAccess.cs`、Editor `GASWatcher` 和 `AbilitySystemBinding` 3 个图依赖；AutoChess lifecycle、catalog session、observation、runtime host、command port 与 runner sync 由 runtime access wrapper 间接分发。按 capability 分组时仍可合并为 Adapter / Editor / Runtime Binding 三类。
2. Runtime 主依赖社群当前为 146 files / 2227 indexed symbols，dependency edges 为 internal 604、boundary 133、incoming 101、outgoing 32。这个图证据说明 Shell、Core、Definition、Debugger 和 schedule 仍深度邻接；后续重划分必须交还 dependency graph / owner map 证据，不能只用命名或文件夹移动证明职责完成。
3. Owner-local fact lane 当前是 Attribute / ASC command fact 的扩展正向切片：ASC 本地 fact buffer、ASC command resolve、pending AttributeDelta、hand-written instant reduce、execution output modifier apply、FramePrepare 清理、CoreSimulation flush 和 Debugger counter 已存在；但 BoundaryProjection 仍从 stream fact 消费，EffectCommand / SetByCaller / TypedSimulationFact 仍没有退出 singleton current carrier。

这些校准继续支持本文件原结论：端到端链路已具备 DOTS backbone，但目标态还必须把多 capability Shell、singleton carrier、generated lifecycle owner、Debugger / Cue materialization 和 AutoChess adapter raw ECS 访问逐项收权。

## 不能推出的结论

1. 不能因为 Runtime `SystemAPI.Query=0`、`CreateEntityQuery=0` 就写成 DOTS 性能优秀；Debugger / Cue `ToEntityArray` 和 runner sync 仍需要独立计时、频率和污染隔离。
2. 不能因为 generated runtime type 缺失已 fail-fast、active-effect lifecycle owner 已退出 SourceGenerator 输出，或 `ActiveEffectLifecycleOwnerSystems.cs` 当前磁盘缺失，就写成 SourceGenerator 职责边界完成；`RuntimeLifecycleMigration` artifact 当前为 0，但 system budget、manifest/report/file/schedule 对账、catalog lifetime / dispose owner、type / assembly 负例和防回流验证仍未闭合。
3. 不能因为 active effect slot SourceAttribute snapshot key / gather job 存在，或 TagRequirement all-any-none 已进入 generated catalog，就写成 active effect lifecycle store-only、magnitude snapshot lane release-ready 或业务 tag 组合全覆盖；还缺容量压力、spill、非零业务配置和规模 profile。
4. 不能因为 AutoChess x50 或 validation report 通过，就写成 AutoChessDemo 测试链完善；Goal 停止条件仍缺 x100 / x1000、Unity Test Runner、Profiler / Journaling enabled 和 SourceGenerator / Luban 重跑。
5. 不能把 `GASRuntimeShell` 注释中的 Thin Shell 语义当成当前事实；当前事实以 direct consumers、暴露 capability 和内部 ECS handle 解析为准。
6. 不能因为 `OwnerLocalGameplayFactBuffer` 和 `GameplayOwnerLocalFactFlushSystem` 已存在，就写成 GameplayFact 目标态完成；当前只是 Attribute / ASC command fact 的多写入面正向切片，且 flush 后仍回到现有 stream fact export，generated 写入面仍要按 `MigrationProofOnly` 审查。

## 对任务领取的事实约束

1. R1/R6 领取前必须复核 `GASRuntimeShell` direct consumers、AutoChess host / observation / lifecycle / ticker 对 World、`EntityManager`、runtime singleton 和 job drain 的依赖。
2. R2/R3 领取前必须复核 `GASRuntimeStreamOwnerPlanner.CreateCurrent()` 的 current carrier / target carrier / scale status，以及 `GEEffectCommandSpecStream` 的 singleton buffer 写入点。
3. R4/R8 领取前必须复核 Debugger / Cue `ToEntityArray` owner 分类、observation materialization counter、performance / diagnostic pass 分离和 official capture state。
4. R5 领取前必须复核 generated runtime artifact 的 `ISystem` / `OnUpdate` / lookup / ECB / NativeContainer 命中，并把 pure glue 与 lifecycle owner 分开验收。
5. R7 领取前必须复核 active effect lifecycle owner 是否仍由手写 Runtime lane 承接、generated lifecycle 是否回流、以及 active effect slot snapshot lane 是否具备 capacity / spill / lane evidence。
