## 重新划分事实结论

当前架构已经具备可以继续保留的 DOTS physical backbone、手写 active-effect owner、generated catalog / pure glue 和 structured evidence；但它还没有达到“纯血 ECS Runtime Core”。核心差距不在于是否使用 ECS API，而在于 interface 仍然太浅：Shell 暴露 ECS handle，stream carrier 混合多语义数据，command resolve 与 active-effect owner 内部实现过宽，CodeGen 模板混合多类 artifact owner，Debugger / Presentation / AutoChess 仍需要更清晰的 cost domain。

因此，本轮事实结论是：

1. OOP 层只能继续向 Application Shell / Runtime Boundary capability 收缩，不能作为 gameplay runtime 中间层扩大。
2. Runtime Core 的真实 owner 应以手写 `ISystem` / job / owner-local store / deterministic fan-in / StructuralCommit / BoundaryProjection 划分，而不是以旧 helper、generated artifact 或 adapter 名称划分。
3. SourceGenerator 当前应被消费为 Definition / Blob / lookup / pure glue / validation 资产；generated lifecycle 当前已退出，但 release-ready 还需要负例验证和防回流。
4. Debugger / 日志应被消费为 evidence 和 derived export；它必须帮助定位 system、carrier、lookup、structural playback、allocation 和 observation materialization 热点，不能反向驱动 Core。
5. AutoChessDemo 当前仍是业务验收 Shell；它的 x50 / x100 / x1000、Profiler / Journaling、headless / scene runner 和 structured evidence 才能证明目标态链路，而不是证明 Core 已经完成。
