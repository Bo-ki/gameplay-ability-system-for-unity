## 当前结论

当前 Runtime 已经不再是完整的旧 OOP pipeline，也不能继续用“全局 EventBus + request entity lifecycle + 大量主线程 query”这类旧口径描述。当前真实形态是：

```text
Layer 1 Application Shell / Demo
  -> Layer 2 Runtime Boundary command/read/diagnostics adapter
  -> Layer 3 GAS Runtime Core 5 段 FixedStep physical group
  -> Layer 4 generated definition catalog / runtime glue
```

这说明架构方向已经从旧式 OOP 中间层迁出，但还没有达到“纯血 ECS GamePlay Core”。当前最深的问题不是有没有 `ISystem`，而是 **Core 的数据接口仍不够深**：singleton stream、generated instant / execution delta record、`GASRuntimeShell` assembly/internal capability 面、Boundary structured projection 的证据面、pre-tick / execution SourceAttribute snapshot lane 缺口，以及 AutoChess adapter 对 RuntimeShell 能力面的依赖仍把实现细节泄露到边界层和生成链。active mutation 跨 owner SourceAttribute 已在 2026-06-07 进入 read-only snapshot lane；execution output typed fact 已开始从 structural ECB singleton append 迁到 `NativeStream` deterministic merge；后续只保留容量 / spill、merge cost 与真实配置语义证据。

### 重新划分后的当前事实结论

1. 当前最深的正向模块不是 Shell，而是 5 段 physical backbone、owner chunk applicator、registered/cache singleton owner、generated immutable catalog 和 structured evidence。
2. 当前最浅的 interface 是 `GASRuntimeShell`、`EffectRuntimeUtility`、singleton stream carrier，以及 generated marker / hand-written owner / schedule / report 对账面；这些模块的调用方或审查者仍需要理解 ECS 句柄、lookup、singleton、capacity、dependency 或 generated artifact owner。
3. 后续架构审查应把 `RunnerSync` 与 `DiagnosticsSink` 从业务 Shell 中拆出；只要 `CompleteAllTrackedJobs`、observation materialization 或 derived export 与 command / snapshot public seam 共用同一 ECS handle，就不能判定 Shell 完成。
4. 后续 SourceGenerator 审查不能只看 `GeneratedRuntimeSystemRegistrationHits=0`；只要 runtime-visible generated artifact 仍拥有 `ISystem`、`OnUpdate`、lookup、ECB 或 NativeContainer owner，就必须保留 `MigrationProofOnly` 退出任务。
5. 后续 Fan-in 审查不能只看是否替换成 `NativeStream`；必须同时证明 sort key、merge order、segment count、capacity / spill、allocator / dispose、battle hash 和 Debugger evidence。
