# 架构重划分审查事实

> 最近复核：2026-06-08 | Owner：`00-当前架构事实` | 范围：`Assets/GAS/Runtime`、`Assets/GAS/Generated/CodeGen/Runtime`、`Assets/AutoChessDemo`

本文件记录本轮“纯 ECS Core + OOP Shell / Thin Adapter + Debugger + Luban SourceGenerator”重划分审查后的当前事实。它只说明现实代码已经做到哪里、仍然暴露哪些架构问题，以及这些问题为什么必须继续拆分；目标态设计见 `../01-目标态架构共识/16-纯ECS内核与边界重划分Spec.md`，可执行任务见 `../02-主线任务树/GAS架构重划分主线任务.md`。

## 当前结论

当前 Runtime 已经不再是完整的旧 OOP pipeline，也不能继续用“全局 EventBus + request entity lifecycle + 大量主线程 query”这类旧口径描述。当前真实形态是：

```text
Layer 1 Application Shell / Demo
  -> Layer 2 Runtime Boundary command/read/diagnostics adapter
  -> Layer 3 GAS Runtime Core 5 段 FixedStep physical group
  -> Layer 4 generated definition catalog / runtime glue
```

这说明架构方向已经从旧式 OOP 中间层迁出，但还没有达到“纯血 ECS GamePlay Core”。当前最深的问题不是有没有 `ISystem`，而是 **Core 的数据接口仍不够深**：singleton stream、generated instant / execution delta record、`GASRuntimeShell` assembly/internal capability 面、Boundary structured projection 的证据面、pre-tick / execution SourceAttribute snapshot lane 缺口，以及 AutoChess adapter 对 RuntimeShell 能力面的依赖仍把实现细节泄露到边界层和生成链。active mutation 跨 owner SourceAttribute 已在 2026-06-07 进入 read-only snapshot lane；execution output typed fact 已开始从 structural ECB singleton append 迁到 `NativeStream` deterministic merge；后续只保留容量 / spill、merge cost 与真实配置语义证据。

## 整体架构审查结论（codedb 复核）

本轮使用 codedb 复核 `GASRuntimeShell`、5 段主链、generated runtime、ActiveEffectStore / SpecStream、Debugger / structured log、Definition catalog / SourceGenerator 和 AutoChess adapter 后，当前架构可以更准确地划分为“已有 DOTS backbone 的迁移期 ECS Runtime”，而不是“纯 ECS GAS 内核完成态”。

| 审查域 | 当前事实 | 架构判断 |
|---|---|---|
| Runtime physical backbone | 5 段 `FixedStepSimulationSystemGroup` 子 group 已存在，generated runtime 也由 `GASSystemScheduleContract` 注册进主链 | 物理执行域方向正确；generated type-name registry 对缺失 type 已 fail-fast，不再静默跳过；剩余是 system 数量、phase budget、负例验证和 generated lifecycle 退出证据 |
| OOP Shell / Runtime Boundary | `GASRuntimeShell` 同时解析 World / `EntityManager`、创建 command port、捕获 read model、解析 singleton、执行 job drain | 当前 Shell 是多能力 ECS 句柄 facade，不是目标态 OOP Shell；它把 command、snapshot、diagnostics、bootstrap、definition 和 dependency drain 混在同一 implementation 面 |
| Core data interface | command/spec/delta/fact/active mutation 仍大量依赖 `GEEffectCommandStreamComponent` singleton DynamicBuffer carrier；active mutation 和 pending AttributeDelta 已推进到 ASC chunk-local apply；execution output typed fact 已进入 `NativeStream` collect + deterministic merge | 旧 random lookup 和一部分 structural ECB fact fan-in 风险已明显收窄，但 scale-ready fan-in / store 仍未闭合；真正缺口是 owner-local range、更完整的 NativeStream carrier 替换、capacity/spill/reselect evidence |
| Debugger / 日志 | `GasRuntimeDebugger`、structured log、OfficialToolDiff 和 AutoChess validation export 已存在，且 report projection 已有 Boundary report key | Debugger 方向应从“日志输出”升级为 evidence source；contract counter、runtime counter、official capture、validation evidence 和 derived export 必须分层消费 |
| Luban / SourceGenerator | `GASDefinitionCatalogBlob`、generated lookup、pure resolver 已进入 Runtime；generated lifecycle / query / ECB / lookup owner 仍以 classified `MigrationProofOnly` 存在 | SourceGenerator 的目标价值不是继续扩生成 runtime system，而是收权到 immutable catalog、static lookup、pure glue、validation graph；runtime lifecycle owner 必须回到手写 Core lane |
| AutoChessDemo | AutoChess 已成为业务验收 Shell，report projector 与 unit result snapshot 已消费 `SourceReportKey` / `TargetReportKey`；driver handle、registry command compatibility 和 observation gateway 仍触达 live ECS | Demo 分层比旧 bridge 健康，但 Thin Adapter 未完成；应继续拆成 runtime host、catalog session、entity lifecycle、snapshot / diagnostics gateway、fixed tick runner 的 owner evidence |

因此，当前最应优先治理的是 **接口深度和 owner locality**，而不是继续新增 OOP facade 或继续把迁移 proof 写成目标态。一个模块是否“深”应按以下事实检查：它是否隐藏了 query、allocator、dependency、capacity、merge、structural playback 和 diagnostics owner；如果调用方仍必须知道 `EntityManager`、singleton entity、raw `Entity`、buffer handle 或 generated lifecycle hit，它就还只是迁移期浅接口。

## 模块深度与职责重划分事实

本轮 codedb `module_map` 显示 `Assets/GAS/Runtime` 的主要依赖社群仍是一个 141 files / 1927 indexed symbols 的大模块，中心文件包括 `GASRuntimeEntityArchetypes.cs`、`ActiveEffectStore.cs`、`GASDefinitionTable.cs`、`GASSystemScheduleContract.cs`、`GameplayEffectConfigRegistry.cs`、`GasRuntimeDebugger.cs`、`GASRuntimeQueryLayoutPlan.cs` 和 `ASCCommandBufferResolveSystem.cs`。这说明 Runtime 文件夹已经形成 DOTS backbone，但 Core、Definition、Debugger、Shell、generated runtime 仍在同一依赖社群中强耦合；目录分层不能代表职责完成。

按 module / interface / implementation 的深度审查，当前更合理的现实划分如下：

| 现实模块 | 当前 interface 形态 | implementation 暴露的问题 | 事实判定 |
|---|---|---|---|
| Runtime Backbone | 5 段 physical group + `GASSystemScheduleContract` | generated type-name registry、contract-only phase / lane 仍混在同一 schedule owner | backbone 已存在，缺失 type fail-fast 已落地；lane owner、phase budget 和 evidence owner 还需继续拆 |
| Boundary Shell | `GASRuntimeShell` + `AbilitySystemBinding` + `ASCCommandPort` / `ASCReadModel` | 同一 facade 同时服务 World / `EntityManager`、command port、snapshot capture、singleton resolver、job drain | interface 过浅；需要拆成 command / snapshot / diagnostics / bootstrap / definition capability |
| Active Effect Store | `ActiveEffectStore` + generated active runtime + `EffectRuntimeUtility` | store、global index、cleanup helper、generated lifecycle、debugger、factory 都直接依赖同一 store | store 正在变深，但 lifecycle owner、cleanup owner、capacity evidence 和 generated proof 仍未收口 |
| Effect Runtime Utility | static helper methods | `TryGetStaticDefinitionBlob`、`ApplyInstantEffect`、`ApplyInactiveDurationEffect`、`HasOngoingRequirements`、`TryMergeStackingApplication`、duration activate/deactivate/reactivate、`ShouldReject` 仍为空/固定返回；已实现部分集中在 cleanup / removal | 不是 Runtime lane owner，只能记录为迁移期 helper；目标态应由手写 system/job/store owner 接管 |
| Fan-in / Stream | `GEEffectCommandSpecStream` singleton buffers + execution output fact NativeStream merge | command/spec/delta/mutation/大部分 fact 仍共用 singleton carrier，`MergeParallelCommandFanIn` 仍是 managed list + `EntityManager` 写回 | proof carrier 仍未整体退出；execution output fact 是 R3 迁移切片，不是全 stream scale-ready |
| Debugger / Structured Log | `GasRuntimeDebugger`、structured log、OfficialToolDiff | evidence、derived export、runtime counter 和 official capture 仍需分层；`ToEntityArray` 命中集中在 Debugger observation，当前已输出 observation materialization counter | Debugger 是 Boundary evidence owner，不是 Core 计算层 |
| Cue / Presentation Boundary | Cue managed lifecycle + presentation outbox | Runtime/Cue 文件夹内存在 managed UnityEngine side effect，`ToEntityArray` 用于 managed boundary 批处理 | 可以保留为 Boundary cost，但不得进入 Core hot path 结论 |
| Definition / SourceGenerator | Blob catalog + generated lookup + generated runtime artifacts | pure glue 与 generated lifecycle 并存；validation gate 已分类但未把 lifecycle hit 归零 | Definition 方向正确，SourceGenerator 仍需从 runtime lifecycle owner 中退出 |

Deletion test 结论：`GASRuntimeShell`、`EffectRuntimeUtility`、singleton stream 和 generated lifecycle system 不能直接删除，因为调用复杂度会外溢；但它们当前 interface 没有隐藏足够多的实现复杂度，调用者或审查者仍要理解 ECS 句柄、global singleton、store cleanup、capacity、dependency 和 generated owner。因此这一轮“重新划分”的事实结论是：不要继续新增更大的 facade，而要把这些浅 interface 拆成更小、更深且可证据归因的 capability / lane / store owner。

## 当前重划分

### 1. OOP Shell 不是中间层

`AbilitySystemBinding`、`ASCCommandPort`、`ASCReadModel` 现在更像 Application Shell / Runtime Boundary 入口，而不是 Runtime Core 的中间层。这个方向正确，但当前接口仍有两类残留风险：

1. `ASCCommandPort` 通过 `ASCBoundaryCommandWriter` 直接拿 `DynamicBuffer` 并启用 pending marker。
2. `AbilitySystemBinding.Commands` 暴露 `ASCCommandPort`，`AbilitySystemBinding.TryResolveRuntimeEntityForBoundary(out Entity)` internal 面、`ASCCommandPort.RuntimeEntity` internal 面和多处 `Request*` 返回值仍允许 assembly 内 raw `Entity` 传播；`RequestGameplayEffectTo` / `RequestActivateAbility` 的 target 已主要收缩为 `ASCHandle`，但 boundary-adapter raw entity 解析仍是迁移面。
3. `ASCReadModel` 已在构造时捕获 level、tag mask、attribute、presentation event 快照，getter 不再直接读 `EntityManager` / `DynamicBuffer`；但 capture 动作仍由 Shell/Boundary 侧直接触达 ECS。
4. `GASRuntimeShell` 当前还是多能力句柄口：同一个 facade 服务 Runtime bootstrap、command port、read model、diagnostics singleton、job drain 和 Editor watcher。它把“业务 Shell 可见 interface”和“Boundary implementation 可用 ECS handle”混在一起，导致 owner 分类必须靠调用点人工判断。
5. 这类能力必须继续收缩到 Layer 2：Shell 只持有 opaque ASC handle / target ref；写入只生成 command record，读取只消费由 BoundaryProjection 统一产出的 snapshot / ring buffer；Editor watcher / Debugger 只能走只读 diagnostics evidence，不直接复用业务 Shell 写句柄。

### 2. Thin Adapter 必须继续变薄

AutoChess 的 `Integration/GasCore` 已把业务层对 GAS 的调用集中到一个 adapter facade，并拆出 runtime host、catalog session、observation gateway、lifecycle、ticker、contracts 等文件，这是正向事实。但 internal Shell capability 仍能把 `EntityManager` 交给 adapter implementation；host 直接负责 runtime world / tick group / job drain，observation gateway 直接重置和读取 Debugger / Replay singleton，lifecycle 直接写 demo component 与 driver store，接口仍不够深。目标态需要让这些 capability 继续收缩为：

1. `BattleRuntimeHost`：World / SystemGroup / fixed tick owner。
2. `BattleCatalogSession`：Definition catalog 安装和释放。
3. `BattleEntityLifecycle`：ASC / driver / unit structural request owner。
4. `BattleObservationGateway`：Replay / Debugger / Official diff snapshot。

这些子 owner 可以仍在同一个 adapter implementation 内，但对外接口不得暴露 `EntityManager` 或 GAS singleton。

### 3. Runtime Core 已 ECS 化，但还未 store-ready

当前 Core 已有 `ISystem`、stored query、ECB gate 和 generated catalog。真正不达标的是数据承载：

1. `GEEffectCommandStreamComponent` singleton owner 仍同时承载 command / set-by-caller / spec / mutation / fact；其中 execution output fact 的 producer 已开始通过 NativeStream merge 写入，但最终 typed fact buffer 仍是 singleton proof/migration carrier。
2. `GASActiveEffectMutationApplySystem` 虽已 job 化、owner 排序并按 owner range 获取 store/slot/snapshot，但仍从 singleton buffer 收集命令，且 helper 内仍通过 `BufferLookup` / `ComponentLookup` random access 写属性、tag、ability 等派生状态。
3. 这类实现可以作为 `MigrationProofOnly`，但不能作为 DOTS 优秀水平。后续必须按 target / owner 分组，形成 owner-local range 或 chunk-local applicator。

### 4. Debugger 是 evidence owner，不是日志系统

当前 Debugger 已有 counter 和 official diff 工具，但目标应从“能输出日志”升级为“能定位 DOTS API 健康度和性能热点”。最低事实字段应覆盖：

1. physical group timing 和 kernel lane timing。
2. command/spec/delta/fact/cue/presentation 计数。
3. global buffer pressure、random lookup count、lookup update count。
4. structural playback 来源和 phase。
5. proof-only API、reselect trigger、official tool capture state。

没有这些字段时，AutoChess x50/x1000 跑通只能证明功能，没有证明 DOTS 性能优秀。

### 5. Luban + SourceGenerator 已进入 Runtime，但仍需收权

当前 generated catalog 已被 Runtime 和 AutoChess 消费，这是正向事实。后续重点不是“多生成代码”，而是让 SourceGenerator 只生成 Runtime Core 可消费的 immutable definition、static lookup、pure glue、validation graph，不生成或隐藏 runtime lifecycle owner。

### 本轮结论

当前 GAS 已有可继续演进的 DOTS backbone，但“纯血 ECS GamePlay Core”还没有完成。最新事实不支持继续建设更大的 OOP 中间层，也不支持把 generated lifecycle 当成 SourceGenerator 成熟形态。正确的重新划分应把 `GASManager` / `GASRuntimeShell` 降为 bootstrap 与 Boundary capability implementation，把 `GEEffectCommandSpecStream` 降为迁移期 carrier，把 generated runtime lifecycle 降为 `MigrationProofOnly`，把 Debugger / Cue / AutoChess observation 从 Core performance pass 中拆出。
