# P0 致命缺陷

> 最近审查：2026-06-02 | 事实源：当前 Runtime / Generated Runtime / AutoChessDemo 代码

P0 只记录会直接破坏 Runtime 边界、结构变化治理、hot path 可扩展性或证据可信度的问题。旧文档中的 `S*` 文件名、旧 group 名称和“22 个 ToEntityArray 热路径”不再作为当前 P0 事实。

## P0-A：Runtime Boundary 仍可同步创建 request entity

`ASCCommandGateway` 仍直接通过 `GASManager.EntityManager` 创建 request entity：

| 路径 | 代码事实 |
|---|---|
| `Dispose()` | 创建 `ASCDestroyRequest` |
| `Init()` | 创建 `ASCInitializeRequest` |
| `RequestRemoveGameplayEffects()` | 创建 `GERemoveRequest` |
| `CreateAbilityCommandRequest()` | 创建 `AbilityCommandRequest` |
| `CreateAscCommandRequest()` | 创建 `ASCCommandRequest` |

这意味着外部 facade 仍可以绕过当前 `GASCommandResolveSystemGroup` 的 command sink 约束，直接把 entity 写进 World。当前结构变化 gate 已经存在，但 boundary 写入口还没有被完全纳入 gate。

**当前要求**：新增/迁移 API 时，优先写入明确 command sink / request stream；不要继续扩张 facade 同步 `CreateEntity()` 路径。

## P0-B：核心系统仍存在同步等待

`state.Dependency.Complete()` 当前命中 10 处：

| 文件 | 风险 |
|---|---|
| `ASCDestroyRequestSystem.cs` | destroy request scan 后同步消费 |
| `ASCDestroyFinalizeSystem.cs` | finalize 多段 job 后同步消费 |
| `AttributeThresholdAbilityLifecycleRequestSystem.cs` | threshold lifecycle 同步消费 |
| `GEExecutionCalculationSystem.cs` | execution calculation candidate 同步消费 |
| `GEExecutionCalculationOutputModifierSystem.cs` | output modifier / attribute candidate 同步消费 |
| `RuntimeActiveEffect.gen.cs` | active effect pre-tick / remove scan 后同步消费 |

destroy/finalize 可以作为低频边界单独评估，但 `ExecutionCalculation` 与 generated active effect tick/remove 属于 CoreSimulation 风险，必须优先拆成可解释的 job chain 或 deterministic candidate merge。

## P0-C：generated runtime 已进入主链但仍是主线程 proof 形态

`RuntimeSystemRegistration.gen.cs` 已把 7 个 generated systems 注册到当前主链：

- `AbilityCatalogCommitSystem`
- `GEEffectCommandCatalogNormalizeSystem`
- `GEEffectSpecBuildSystem`
- `GASActiveEffectMutationApplySystem`
- `GASAttributeSetReduceApplySystem`
- `GASActiveEffectPreTickSystem`
- `GASActiveEffectRemoveSystem`

这些系统不是纸面 Contract，已经修改 runtime state。当前仍存在：

1. `SystemAPI.Query` 主线程 foreach。
2. DynamicBuffer for loop。
3. `state.Dependency.Complete()`。
4. 通过 singleton stream owner 承载 command/spec/delta/fact/active mutation。

生成代码身份不能豁免 DOTS 规则。凡是 generated system 写 attribute、active effect、fact 或结构变化，都必须有 query/job/dependency/ordering 证据。

## P0-D：singleton stream owner 被当作多条 hot path 的事实源

`GEEffectCommandStreamComponent` owner 当前承载至少以下 buffer：

- `AbilityCommandBuffer`
- `GEEffectCommandBuffer`
- `GESetByCallerValueBuffer`
- `GEEffectSpecBuffer`
- `AttributeModifierBuffer`
- `ActiveEffectMutationBuffer`
- `GameplayEventBuffer`

这使 command/spec/delta/fact 迁移链能跑通，但它是 proof-only carrier，不是 scale-ready 架构。所有 producer/consumer 都汇聚到单 entity DynamicBuffer，后续 x50/x1000 profile 很容易把 buffer pressure、dependency complete、deterministic ordering 问题放大。

## P0-E：结构变化集中化缺少证据闭环

当前 `GASStructuralCommitSystemGroup` 和 `Begin/EndGASStructuralCommitECBSystem` 已经是真实物理 gate。正向事实成立，但还不能宣称结构变化已经全部收口：

1. Boundary facade 仍直接创建 request entity。
2. Config/prototype/demo bridge 仍直接 `EntityManager.CreateEntity()` / `DestroyEntity()`。
3. generated active effect 通过 `EndGASStructuralCommitECBSystem.Singleton` 记录结构变化，但需要 Journaling 证明 playback 相位、数量和来源。
4. `GasRuntimeOfficialToolDiff` 已能用 `EntitiesJournaling` 抓结构变化记录，但文档不能把工具存在当完成证明。

## P0-F：Observation 成本与 CoreSimulation 成本仍需隔离

旧“22 个 ToEntityArray 热路径”已经不成立；当前 `ToEntityArray` 主要在：

- `GasRuntimeDebugger` observation 路径
- `AutoChessBattleDefinitionCatalogBuilder` 低频 catalog singleton 查询

新的 P0 不是 `ToEntityArray` 数量，而是证据污染：如果 Debugger、Replay、Presentation、Official diff 的同步 query 成本与 CoreSimulation 混在同一性能结论里，后续架构判断会失真。

## 当前 P0 退出条件

1. `ASCCommandGateway` 不再直接创建 request entity，或其创建被明确纳入 command sink / structural commit owner。
2. `ExecutionCalculation` 和 generated active effect tick/remove 不再用无解释的 `Complete()` 主线程消费。
3. singleton stream owner 的每类数据都有明确迁移去向或容量/ordering 证据。
4. `GasRuntimeOfficialToolDiff` / Profiler / Debugger counters 能证明结构变化只在预期 phase 发生。
5. CoreSimulation 性能报告与 Observation/Debugger 成本分离。
