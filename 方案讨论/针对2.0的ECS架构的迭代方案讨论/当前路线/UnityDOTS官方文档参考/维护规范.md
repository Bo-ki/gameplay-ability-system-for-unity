# UnityDOTS 官方文档参考 — 维护规范

本文件定义 UnityDOTS 官方文档参考知识库的维护规范：如何从官方文档提取内容、如何组织文档切片、文档模板、自检机制。

## Part A: 文档切片的提取规范

### A.1 提取触发条件

| 触发条件 | 提取动作 |
|---|---|
| 新任务涉及未覆盖的 DOTS API | 在任务执行前提取该 API 的技术领域文档 |
| 现有 ISSUE 诊断暴露了官方文档未知的约束 | 补充到对应技术领域文档的规则/陷阱节 |
| PackageCache 版本更新 | 检查 `Documentation~` 变更，更新受影响的领域文档 |
| 自检发现官方文档有遗漏信息 | 补充提取 |

### A.2 提取流程（四步）

```
步骤 1: 定位官方文档源
  → PackageCache Documentation~ 为第一性依据（README.md 中有版本和路径表）
  → 在线文档仅作补充阅读和版本差异对比
  → 记录：包名、版本号、PackageCache hash、具体 .md/.html 文件名

步骤 2: 阅读并识别可提取内容
  → 通读官方文档，识别以下四类可提取内容：
     a) API 机制：这个 API 怎么工作？关键概念和生命周期？
     b) 性能特征：成本模型、限制、扩展行为？
     c) 使用约束：官方推荐/禁止的使用方式？
     d) 版本特定信息：deprecation、breaking changes、已知问题？

步骤 3: 筛选 → 只提取对 EX-GAS 项目有实际影响的
  → 问：这条信息是否会影响 EX-GAS 的代码决策？
    是 → 提取
    否 → 跳过（例如：纯 Editor 工具 API 对 Runtime Core 无影响）
  → 问：这条信息是否已存在于当前知识库中？
    是 → 更新而非重复
    否 → 新增

步骤 4: 翻译为 EX-GAS 工程语言
  → 官方原文: "Structural changes are the primary cause of sync points"
  → EX-GAS 翻译: "ISystem.OnUpdate 或 job 内不得直接调用 CreateEntity/AddComponent/RemoveComponent/DestroyEntity"
  → 附证据: "> 来源：com.unity.entities@1.4.6, performance-sync-points.md"
```

### A.3 提取内容的归属判断

| 提取到的内容类型 | 归属到文档的哪一节 |
|---|---|
| API 怎么工作、生命周期、关键概念 | `核心概念` |
| 官方推荐/禁止的使用方式、性能约束 | `编写规范`（生成或更新规则条目） |
| 典型用法代码示例、常见错误示例 | `模式与反模式` |
| 静默退化、不报错但变慢的陷阱 | `常见陷阱` |
| 官方文档文件名和章节引用 | `官方证据` |
| 对 EX-GAS 架构/ISSUE/代码的具体影响 | `EX-GAS 项目解读` |

## Part B: 文档切片的维护规范

### B.1 文档类型定义

本知识库包含四种文档类型：

| 类型 | 定义 | 存放位置 | 示例 |
|---|---|---|---|
| **主题索引** (_index.md) | 主题门户，链接所有独立文件 + 表达关系 + 阅读路径 | `主题/{TopicFolder}/_index.md` | `System-World-SystemGroup/_index.md` |
| **API 与 EX-GAS 解读** | 共享上下文的 API 机制 + EX-GAS 项目解读 | `主题/{TopicFolder}/API与EX-GAS解读.md` | `System-World-SystemGroup/API与EX-GAS解读.md` |
| **规范/模式文件** | 单条规则或单个 CASE 的独立文件 | `主题/{TopicFolder}/{CODE}.md` | `SYS-01.md`、`CASE-16.md` |
| **元信息文档** | 跨主题的索引、选型指南、流程规范（不变） | `元信息/` | `90-规则编号索引.md` |

### B.2 聚合原则（高内聚）

**一个技术领域文档 = 一个 DOTS 技术领域的所有相关知识。**

聚合判断标准：
- **共享 API 上下文**：如果不理解 API X 的机制就看不懂某条规范，该规范属于 API X 的领域文档
- **共享诊断上下文**：如果两条规则被同一个 ISSUE 命中、在同一类代码文件中检查，它们属于同一领域

### B.2.1 Primary Owner 模型（跨主题规则处理）

每条规则/模式有且仅有一个 Primary Owner 主题。规则文件只存放在 Primary Owner 的文件夹中。

**判定规则：**
1. 规则涉及的 API 机制归属哪个主题 → 该主题是 Primary Owner
2. 如果多主题涉及同一 API → 选择"该规则最常被引用的语境"所在的主题

**非 Primary Owner 的引用方式：** 在 `_index.md` 的"跨主题引用"节中以表格形式列出，不复制规则文件。

### B.3 拆分触发条件（低耦合）

| # | 条件 | 拆分动作 |
|---|---|---|
| S1 | 覆盖 ≥3 个可独立描述、互不依赖的子领域 | 每个子领域独立为一个技术领域文档 |
| S2 | 规则覆盖不同的 API 机制 | 按 API 机制边界拆分 |
| S3 | 一个规范/概念的理解不依赖另一个规范/概念 | 分离为独立文档 |

**不设硬性行数阈值**——行数是领域边界模糊的症状而非原因。

已确定的合并/拆分决策：
- ECB + 结构变化 → 合并（ECB 的唯一目的就是做结构变化）
- Enableable → 独立（有独立的 API 机制，不依赖 ECB 概念）
- Transform/层级 → 独立领域（涉及专门的 Transform API）

### B.4 命名规范

- 主题文件夹：`{TopicFolderName}/`
- 主题索引：`_index.md`（固定名称）
- API+EX-GAS 解读：`API与EX-GAS解读.md`（固定名称）
- 规范文件：`{CODE}-{NNN}.md`（不允许文件名带描述，如 `SYS-01.md` ✅，`SYS-01-权威计算.md` ❌）
- CASE 文件：`CASE-{NNN}.md`

### B.5 规则编号的生命周期

- 规则的权威定义在其 Primary Owner 主题文件夹中的独立规则文件
- `90-规则编号索引.md` 的"Owner"列指向 `主题/{TopicFolder}/`
- 新增规则：在 Primary Owner 主题文件夹中创建 `.md` 文件，更新索引和 `_index.md`
- 废弃规则：在索引中标记 `[已废弃]`，不从规则文件中删除（保留历史）

## Part C: 文档切片的内容模板

### C.1 _index.md 模板

`_index.md` 的格式以现有文档为准——每个主题创建一个 `_index.md`，作为该主题的门户首页。内容结构参考已有约定的章节顺序（核心概念、编写规范、模式与反模式、常见陷阱、验收指标等），具体格式不限。

### C.2 API与EX-GAS解读.md 模板

`API与EX-GAS解读.md` 聚合 API 机制详解和 EX-GAS 项目解读两部分。格式参考现有主题中 `核心概念` 和 `EX-GAS 项目解读` 章节的写法，具体格式不限。

### C.3 规范文件模板

```markdown
# {CODE}-{NNN}: {规则标题}

**Owner 主题：** `{TopicFolder}/`

**来源：** 官方文档引用

**规则声明：** 一句话描述 DO/DON'T

**为什么：** 违反后果

**EX-GAS 关联：** 相关 ISSUE 或代码路径

**检查方法：** 如何自动/手动验证
```

### C.4 CASE 文件模板

```markdown
# CASE-{NNN}: {案例标题}

**Owner 主题：** `{TopicFolder}/`

**场景描述：** 什么业务场景

**方案：** 推荐的实现方式

**反方案：** 不推荐的实现方式（如有）

**验证：** 如何验证正确性
```

## Part D: 自检机制

### D.1 自检流程

```
步骤 1 — 溯源检查：官方文档原始参考是否准确？
  1a. 打开 PackageCache 中对应的官方文档源文件
  1b. 对比 API 机制描述是否与官方文档一致
  1c. 对比性能数据/约束是否与官方文档一致
  1d. 检查是否有新版本变更未反映

步骤 2 — 最小披露检查：Agent 查找链路是否足够短？
  2a. 模拟 Agent 从 README 速查表查找典型问题
  2b. 统计跳转次数（目标 ≤2 次）
  2c. 检查 Agent 只读此文档能否获取所需全部 DOTS 参考信息

步骤 3 — 内聚性检查：文档内容是否低耦合高内聚？
  3a. 每条规范是否共享同一 API 上下文？
  3b. 是否存在与本领域 API 无关的内容？
  3c. 是否存在应在本领域但遗漏的规范？

步骤 4 — GAS 解读检查：EX-GAS 视角的切分是否完善？
  4a. 每条规范是否关联了 ISSUE？
  4b. EX-GAS 解读是否具体到代码级别？
  4c. 验收指标是否可用 Debugger/测试验证？
```

### D.2 自检清单

| # | 检查项 | 不合格时 |
|---|---|---|
| 1 | 官方文档源引用准确 | 更新文档 |
| 2 | README → 文档定位 ≤2 次跳转 | 优化速查表 |
| 3 | Agent 读此文档可获取全部 DOTS 参考信息 | 补充内联约束 |
| 4 | 文档内所有规范共享同一 API 上下文 | 拆分不相关规范 |
| 5 | 本领域相关的 PRF/CASE 已归入 | 补充遗漏 |
| 6 | 每条规则有关联 ISSUE（如适用） | 补充链接 |
| 7 | EX-GAS 解读具体到代码文件级别 | 具体化 |
| 8 | 验收指标可用 Debugger/测试验证 | 补充可验证指标 |
| 9 | 不存在本领域 API 无关的冗余信息 | 删除或迁移 |

## Part E: 持续校准

本规范描述的是维护方法。以下情况触发规范更新：
- 新增 DOTS 包或 API 领域 → 评估是否需要新增技术领域文档
- 发现现有领域边界划分导致 Agent 频繁跨文档查找 → 调整聚合/拆分决策
- PackageCache 大版本升级 → 复核全部官方证据引用
