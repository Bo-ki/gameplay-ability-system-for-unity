# 文档覆盖流程

## 职责

本文件维护官方文档结论如何进入行动报告、任务树、目标态 Spec、当前事实和进度状态，确保每次从官方文档学到的东西不会丢失、不会重复发现。

## 核心概念

### 覆盖闭环流程

```
Unity 官方文档读取
    → 提取规则/模式/约束
    → 判断影响范围
    → 反哺对应 owner
    → 行动报告/任务树/Spec/事实/治理规范更新
```

### 各类发现的归属判断

| 发现类型 | 反哺 Owner | 示例 |
|---|---|---|
| 改变目标态设计 | `01-目标态架构共识` | 官方 API 能力改变 Runtime Core phase 设计 |
| 暴露当前实现问题 | `00-当前架构事实/核心问题诊断` | 当前 ECB 使用模式违反官方建议 |
| 改变执行顺序/优先级 | `02-主线任务树` | 新发现需要先修 backbone 再继续功能 |
| 改变流程规范 | 对应主题文件夹内的治理规范 | 需要新的交还检查项 |
| 本轮临时发现 | `04-当前进度状态/迭代摘要` | 本轮验证中的特殊情况 |

## ODF 规则详解

| 编号 | 规则 | 说明 |
|---|---|---|
| `ODF-01` | DOTS 相关任务必须先读 `UnityDOTS官方文档参考/README.md` | 再按任务类型读技术领域文档 |
| `ODF-02` | 行动报告必须列出 PackageCache 实际版本和相关技术领域 | 不得只写"最新版" |

| `ODF-04` | 官方依据暴露当前实现问题 → 反哺 `00-当前架构事实/核心问题诊断` | 附带具体规则编号 |
| `ODF-05` | 官方依据改变任务顺序 → 反哺 `02-主线任务树` | 更新任务优先级和依赖 |
| `ODF-06` | 官方依据改变流程 → 反哺对应主题文件夹内的治理规范 | 更新交还检查项 |
| `ODF-07` | 本轮发现 → 写入迭代摘要 | 判断是否升级为长期事实 |

| `ODF-10` | PackageCache hash、Burst AOT、Baking world、allocator 等环境项进入交还证据 | 完整可复现环境 |

## 官方证据

所有 ODF 规则都可追溯到各技术领域文档中的官方证据表。本文件本身不重复维护官方证据。

## 使用模式与反模式

**正确模式：**
- 发现 → 判断影响 → 选择 owner → 反哺 → 验证
- 行动报告中引用具体技术领域文档，不写"看过官方文档"

**反模式：**
- 读了官方文档但不在行动报告中记录
- 发现的问题只记在对话里，不落文档
- P0/P1 发现无 owner 追踪

## EX-GAS 项目解读

### 当前反哺路径检查

每次 DOTS 相关任务完成后，同步检查：
1. 是否有新的目标态 Spec 需要补充？
2. 是否有当前实现问题需要记录到诊断？
3. 是否有任务顺序需要调整？
4. 是否有新的 CASE 模式需要加入对应技术领域文档？

### 行动报告的最小模板

```
官方文档覆盖检查：
  - PackageCache: Entities e90944159b94 (1.4.6)
  - 读取技术领域: System-World-SystemGroup, Query-Job-遍历, 结构变化-ECB, DynamicBuffer-Chunk-Archetype, API选型基线
  - 适用规则: QRY-01, JOB-01, SC-01, BUF-01, SEL-03
  - 采用: IJobEntity (CASE-02) for AttributeDeltaApply
  - 拒绝: SystemAPI.Query (CASE-01) — 主线程 sync 不可接受
  - 暂不相关: Physics (ODF-15) — 当前无范围技能需求
  - 需要反哺: 更新 00-当前架构事实 — ECB 使用模式偏差
```

## 常见陷阱

1. **ODF-09..18 被视为"模板填空"**：每个 ODF 项必须真正判断相关/不相关
2. **反哺延迟**：发现放在迭代摘要后不下沉到长期事实
3. **旧聚合文档残留**：内容已迁移但旧文件未删除

## 验收指标

1. 行动报告和交还内容能定位到具体技术领域文档，不只是"看过官方文档"
2. 每个 P0/P1 发现都有 owner 和反哺状态
3. 已解决问题从当前事实中归档，不留在活跃诊断里污染任务输入
4. 行动报告中 ODF-09..18 每项都有相关/不相关的明确说明
