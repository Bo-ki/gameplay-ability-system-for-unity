# 当前架构事实与问题诊断规范

## 适用范围

本规范约束 `../00-当前架构事实/` 的维护方式，重点约束 `核心问题诊断.md` 和 `核心问题诊断/` 子目录。

当前架构事实只回答“当前版本已经证明了什么”。目标态设计进入 `../01-目标态架构共识/`，任务拆解进入 `../02-主线任务树/`，流水记录进入 `../迭代记录/`。

## 核心原则

1. 当前事实必须有当前证据，不接受只来自历史方案的旧诊断。
2. 一个核心问题一个文档，索引文件只保留看板和总诊断。
3. 问题诊断必须能被 Agent 当作任务前置上下文直接阅读。
4. 问题状态必须定期复核；解决的问题归档，不继续占据当前看板。
5. 当前事实不写愿景，不写“应该怎么设计”的完整方案；只写问题、证据、影响和目标态入口。

## 问题进入流程

Agent 在执行中发现问题时，按以下顺序处理：

1. 判断是否是“核心问题”。
   - 是：影响 Runtime 主流程、四层边界、配置权威链、Debugger 诊断能力、验收 Demo 边界或任务执行质量。
   - 否：只影响单个文件、单个 API、单个测试断言，进入任务记录或代码注释，不进入核心问题诊断。
2. 收集当前证据。
   - 代码证据：路径和行号，说明结构为什么导致问题。
   - 验证证据：profile、测试结果、异常栈、validation summary。
   - 过程证据：迭代记录、用户明确反馈、已复现的工作流问题。
3. 检查是否已有问题文档。
   - 已有：追加“新增证据”或更新“当前证据 / 影响 / 退出条件”。
   - 没有：创建新 `ISSUE-xxx-短标题.md`。
4. 更新 `00-当前架构事实/核心问题诊断.md` 看板。
5. 如果问题需要改变目标态，先更新 `01-目标态架构共识/` 对应 Spec，再更新任务树。
6. 如果问题只影响执行优先级，更新 `02-主线任务树/` 或 `04-当前进度状态/`，不要把任务状态写回问题文档。

## 证据等级

| 等级 | 可进入核心问题诊断 | 说明 |
|---|---|---|
| A | 是 | 当前代码行号 + 当前 profile / 异常 / 测试结果共同证明 |
| B | 是 | 当前代码行号 + 当前架构图 / 模块索引 / 迭代记录证明 |
| C | 谨慎 | 用户反馈 + 可复现路径，但还缺行号或验证结果；必须标注待补证据 |
| D | 否 | 历史方案旧诊断、主观猜测、一次性局部代码味道 |

历史方案只能作为“诊断写法来源”或“设计思路来源”，不能作为当前事实证据的唯一来源。

## 单问题文档模板

```md
# ISSUE-xxx 短标题

## 状态

| 字段 | 内容 |
|---|---|
| 状态 | Active / Monitoring / Resolved / Archived |
| 严重度 | P0 / P1 / P2 |
| 最近复核 | YYYY-MM-DD |
| 所属层 | Application Shell / Runtime Boundary / GAS Runtime Core / Definition & Generation / 文档治理 |

## 问题陈述

一句话说明当前问题本质。

## 当前证据

代码证据、profile 证据、异常证据、验证记录。

## 执行路径

从入口到后果的链路。

## 影响

性能、结构安全、边界、Debugger、任务执行或验收影响。

## 根因反推

该问题说明哪个目标态约束没有兑现。

## 目标态入口

指向具体 Spec。

## 任务入口

指向具体任务树节点。

## 退出条件

问题怎样才算解决。
```

## 状态定义

| 状态 | 含义 | 看板处理 |
|---|---|---|
| Active | 当前仍影响主线设计或实现 | 保留在 `核心问题诊断.md` |
| Monitoring | 已有修复，但仍需要一个或多个验证周期观察 | 保留在看板，降低优先级 |
| Resolved | 已满足退出条件，但尚未归档 | 保留一轮复核 |
| Archived | 已归档，不再作为当前问题 | 从看板移除，移动到 `_归档/` |

## 归档流程

1. 确认退出条件全部满足。
2. 在问题文档顶部把状态改为 `Resolved`，补充解决证据。
3. 经过至少一轮相关验证或后续任务未复发后，将文档移动到 `核心问题诊断/_归档/`。
4. 从 `核心问题诊断.md` 当前看板移除。
5. 如该问题被更大问题吸收，归档文档必须写清“被哪个 ISSUE 合并”。
6. 如果归档问题复发，不直接移回旧文档；创建新 ISSUE，并在新文档里引用旧归档。

## 时效性维护

1. 每次 Goal 交还时，如果改动影响 Runtime 主链、四层边界、Debugger、Luban/generated 或 AutoChess 验收，必须检查 `00-当前架构事实/` 是否需要更新。
2. 每次性能 profile、Scene runtime、batchmode validation 暴露新事实时，先更新对应 ISSUE，再更新任务状态。
3. 每个 Active ISSUE 必须有 `最近复核` 日期。超过 2 个主要迭代未更新，应重新复核或降级归档。
4. 如果当前代码已经不支持某条证据，必须删除或改写该证据，不能让旧行号继续代表当前事实。
5. 当前事实和目标态不一致时，不能直接改目标态迁就当前实现；先在当前事实中记录差距，再决定是否更新 Spec。

## 禁止事项

1. 禁止把历史方案中的旧“当前问题”原样复制为当前事实。
2. 禁止把任务完成清单写进核心问题文档。
3. 禁止没有代码或验证证据就把问题标为 P0。
4. 禁止把同一问题拆成多个重复 ISSUE；新增前必须先搜索现有诊断。
5. 禁止删除已解决问题的历史；必须归档。
