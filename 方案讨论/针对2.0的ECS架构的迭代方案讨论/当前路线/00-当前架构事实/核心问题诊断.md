# 核心问题诊断

## 定位

本文件是当前迭代版本核心问题诊断的索引和看板。每个问题的完整证据链、执行路径、影响、目标态反推和任务入口维护在 `核心问题诊断/` 子目录中。

历史方案参考中的“当前架构问题”基于旧版本快照，只能作为诊断写法和设计思路来源，不能替代这里的当前事实。当前事实必须能追溯到当前代码、当前 profile、当前验证记录或当前文档状态。

## 诊断写法来源

历史方案中值得吸收的是“问题诊断的表达规范”，不是旧结论本身：

1. 先定位具体代码结构，再说明运行后果，例如方案12 直接从 `MCAbilityLogic` / `AbilityLogicBase` / `MCModifiers` 说明 Burst 失效：`../历史方案参考/方案12.md:7-16`。
2. 用代码片段或执行路径证明问题，例如方案14 对 `EntityHelper` 全局 ECB、pending component、deferred command 的问题展开：`../历史方案参考/方案14.md:29-44`。
3. 用业务规模说明问题会被放大，例如方案14 对 Ability O(n) 查找在自走棋场景中的放大说明：`../历史方案参考/方案14.md:46-62`。
4. 用当前架构与目标架构对照反推设计，例如方案15 的 Burst 覆盖、OOP 层定位、Ability 行为、属性计算、Modifier 存储对比：`../历史方案参考/方案15.md:1289-1300`。
5. 对复杂问题给出完整执行路径，例如方案15 的“刺客触发背刺”路径展示 OOP/ECS 往返和事件回调链：`../历史方案参考/方案15.md:2549-2588`。

本目录后续新增问题必须遵守 `架构事实与问题诊断规范.md`。

## 当前总诊断

当前不应继续把问题描述为“缺少某个业务机制”。真正的当前问题是 Runtime Core 主流程尚未从旧 lifecycle / global observation stream 迁移到 phase + stream 驱动模型；同时当前实现还缺少 Unity DOTS 意义上的 Runtime Core Frame Backbone，无法统一归因 query / lookup / allocator / dependency / structural playback / deterministic stream / Debugger evidence。

当前循环顺序应固定为：先优化 GAS Runtime 架构，再回到 AutoChess 做全链路验证和性能日志分析；发现问题后先判断来源于 GAS 架构侧还是 AutoChess 业务侧，再推进对应路线。Runtime Core 未完成前不继续推进 AutoChess 拆分路线。

新增校准要求：后续 Runtime Core 任务不能只引用 GAS 概念和历史方案，必须同时引用 Unity Entities 机制校准 Spec、使用规范 Spec、官方文档研读、API 选型 Spec 和官方案例研读 Spec，明确 SystemGroup、ISystem/job、ECB playback、DynamicBuffer、Enableable、Blob/Baker、Query filter 的落点，并在行动报告中列出适用规则编号和 `CASE-*` 官方案例对照。AM3 / AM5 后续扩张前必须先处理 ISSUE-009，完成 `T1-RuntimeCore-AM2B Runtime Core Frame Backbone`。

后续领取 Runtime 任务前，必须先读本索引和对应 ISSUE 文档；如果任务执行中发现新的系统性问题，先按治理规范补问题诊断，再拆任务或改目标态 Spec。
