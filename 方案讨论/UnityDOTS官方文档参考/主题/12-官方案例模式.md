# 12 官方案例模式

## 职责

本主题维护 Unity 包内 DocCodeSamples、Tests、PerformanceTests 对 EX-GAS 可借鉴的写法，并给出明确采用/拒绝的理由。不把官方入门示例机械搬进 Runtime Core。

**高级/专项 CASE 模式（CASE-21~47）见 [16-官方案例模式-高级](16-官方案例模式-高级.md)。**

## 核心概念详解

### 案例来源与参考方式

| 包 | 案例路径 | 主要覆盖 |
|---|---|---|
| Entities | `DocCodeSamples.Tests/*.cs` | Query、IJobEntity、IJobChunk、DynamicBuffer、Baker、Blob、Prefab |
| Entities | `Unity.Entities.Tests` | 边界行为、异常、安全限制 |
| Entities | `Unity.Entities.PerformanceTests` | 规模化性能基准 |
| Physics | `Samples~` | Physics authoring、query、event、debug display |
| Entities Graphics | `Unity.Entities.Graphics` | 组件边界、conversion、runtime render path |
| Collections | `DocCodeSamples.Tests` | allocator、NativeStream、ParallelWriter |

### 案例评审判别标准

读到官方示例时，按以下标准判断是否适用于 EX-GAS Runtime Core：

1. **执行线程**：示例在 main thread 还是 job？
2. **规模假设**：示例用 10 个 entity 还是 10000 个？
3. **结构变化频率**：示例每帧创建/销毁 entity 吗？
4. **托管依赖**：示例使用 class / delegate / managed object 吗？
5. **确定性**：示例的输出顺序确定吗？

## CASE 规则详解

| 编号 | 模式 | 官方示例特征 | EX-GAS 用法 | 拒绝条件 |
|---|---|---|---|---|
| `CASE-01` | `SystemAPI.Query` 遍历 | 主线程 foreach；自动缓存 query | 仅用于 Debugger 快照、Editor 工具、<100 entity 的 proof | 任何 >100 entity 的 hot path |
| `CASE-02` | `IJobEntity` 遍历 | per-entity 并行；自动生成 query | Runtime Core hot path 主力（普通 per-entity 计算） | chunk 级条件跳过需求 |
| `CASE-03` | `IJobChunk` 遍历 | chunk 级访问；manual entity enumeration | 批量统计、enableable 过滤、非标准遍历 | 简单 per-entity 变换 |
| `CASE-04` | DynamicBuffer | owner-local 可变数组 | ActiveEffectSlot、per-owner delta、outbox | 全局并行 fan-in 唯一通道 |
| `CASE-05` | ECB 延迟结构变化 | 在 job 中记录；playback 统一提交 | 结构变化唯一方式（在 StructuralPlayback phase） | gameplay event bus |
| `CASE-06` | Enableable | `EnabledRefRW` / `EnabledMask` toggle | 高频状态开关（active/inactive、alive/dead） | 低频一次性状态 |
| `CASE-07` | Baker + Blob | Baking 期生成 BlobAsset | Definition & Generation Layer 的 definition 承载 | runtime state 存储 |
| `CASE-08` | Entity Prefab | baked prefab 包含完整 archetype | 真实资源 entity 模板 | Core lifecycle 驱动 |
| `CASE-09` | Physics query | `OverlapAabb` / `Raycast` + `CollisionFilter` | 目标获取输入（候选列表） | GAS 规则裁决 |
| `CASE-10` | Graphics runtime create | `RenderMeshUtility.AddComponents` | Presentation 层真实渲染 | Core 直接添加 graphics component |
| `CASE-11` | Burst FunctionPointer | `BurstCompiler.CompileFunctionPointer` | 动态算法选择 + 批处理粒度 | OOP callback 替代品 |
| `CASE-12` | NativeStream | 并行 fan-in + deterministic merge | EffectCommand fan-in、Delta 收集 | 输出无需确定性时 |
| `CASE-13` | Aspects（已废弃） | `IAspect` 包装组件子集为 C# struct | **禁止新代码使用**。官方已标记 Aspects 为 deprecated，推荐直接使用 component access 和 query 方法。10B Spec 和已有代码中的 Aspect 用法需逐步替换 | 任何新代码；已有代码在重构窗口替换 |
| `CASE-14` | Write Group 写保护 | `[WriteGroup(typeof(T))]` + `EntityQueryOptions.FilterWriteGroup` | Attribute 写保护：当外部系统（如无敌 Buff）需要覆盖属性写入时，向目标组件的 WriteGroup 注册标记组件，源系统自动跳过该 entity | 不需要系统间写覆盖协调时 |
| `CASE-15` | Cleanup Component 生命周期 | `ICleanupComponentData` + 三阶段 job（init → process → cleanup） | granted tag/ability 的 cleanup 路径：entity 销毁后 cleanup component 保留，cleanup system 负责释放后移除 cleanup component | 不需要 destroy 后清理的简单 entity |
| `CASE-16` | SystemGroup Allocator | `SetRateManagerCreateAllocator` + `DoubleRewindableAllocators` + `SetGroupAllocator` | Frame Prepare SystemGroup 的 allocator 管理：为 Runtime Core backbone 的 `GasRuntimeFramePrepareSystemGroup` 建立 per-group scratch allocator | 临时 allocator 够用时 |
| `CASE-17` | ICustomBootstrap 多世界 | `ICustomBootstrap.Initialize` + `DefaultWorldInitialization.GetAllSystems` | EX-GAS 多 World 场景（如 Server/Client 分离、AutoChess headless validation world）：无头 AutoChess runner 必须通过 ICustomBootstrap 创建 `FixedStepTime(1.0f/60f)` 独立 World，各 SystemGroup 通过 `[UpdateInGroup]` 分发到正确 World；不隐式依赖 Editor `World.Time` 或 `VariableStepTime` | 单 World 默认场景 |
| `CASE-18` | `chunk.DidChange` 精细变更检测 | `chunk.DidChange(ref TypeHandle, LastSystemVersion)` 在 IJobChunk.Execute 内逐 chunk 判断 | **替代 `SetChangedVersionFilter`**：在 IJobChunk 内部按 component type 逐一检查 chunk 是否变更，比 query 级 filter 更灵活。GAS 场景：属性脏标记检测、effect 重评估跳过、多输入源的部分变更判断。配合 `System.LastSystemVersion` 使用 | 简单 per-entity 遍历（用 IJobEntity + WithChangeFilter 更简洁） |
| `CASE-19` | TransformUsageFlags 烘焙优化 | `TransformUsageFlags.Dynamic` / `Renderable` / `WorldSpace` / `ManualOverride` | AutoChess Baking 优化：静态棋子/建筑用 `Renderable`（不生成 `LocalTransform`+`Parent`），动态单位用 `Dynamic`（生成完整 transform hierarchy）。entity prefab 自动标记为 Dynamic | 纯 ECS 创建 entity（不经过 Baking） |
| `CASE-20` | `EnabledMask` 批量 Enableable 操作 | `chunk.GetEnabledMask(ref TypeHandle)` + index-based enable bit 设置/读取 | 高频批量 enableable 切换：如批量激活/停用 effect、批量复活/击杀 unit。在 IJobChunk 中按 index 操作 `EnabledMask[i] = false`，比逐 entity `SetComponentEnabled` 快 10-100x。注意：disabled component 仍可被 `ComponentLookup` 读取和修改 | 简单逐个 entity 操作（用 `EnabledRefRW<T>` in IJobEntity 更简洁） |

> **CASE-21 ~ CASE-47（高级 ECB / Chunk 优化 / Baking 高级 / Streaming / 系统数据模式）见 [16-官方案例模式-高级](16-官方案例模式-高级.md)。**

### 案例采用/拒绝示例

```
// 行动报告中应这样表达

采用 CASE-02 (IJobEntity) for AttributeDeltaApply：
  - 官方示例模式：per-entity Execute + ref component
  - 本项目的适配：增加 owner-local buffer lookup
  - 边界判断：简单 per-entity delta add，不需要 chunk 级操作

拒绝 CASE-01 (SystemAPI.Query) for EffectCommand ingest：
  - 官方示例是 10 个 entity 的主线程遍历
  - 本项目的 EffectCommand ingest 在 x50 下每秒 >5000 命令
  - 主线程 sync point 不可接受
  - 替代：IJobChunk + sorted command buffer
```

## EX-GAS 项目解读

### 对行动报告的强制要求

每个 DOTS 相关任务交还时必须说明：
1. 采用/拒绝哪些 `CASE-*` 模式
2. 官方示例中的什么边界或假设不适用于 EX-GAS
3. 如果当前是 proof-only，什么指标触发重新选型

**示例格式：**
```
采用：CASE-02 (IJobEntity) - Attribute delta apply
拒绝：CASE-01 (SystemAPI.Query) - 主线程 sync 不可接受
暂不相关：CASE-09 (Physics) - 当前无范围技能需求
待重新选型触发：Buffer spill rate > 50% → 考虑 CASE-12 NativeStream
```

### 常见误用警告

- **入门示例≠规模化方案**：官方入门示例常使用 `SystemAPI.Query`、小规模 entity、主线程 foreach。这些是教学工具，不是 Runtime Core hot path 方案
- **Tests 不是性能参考**：Unit tests 追求正确性和可读性，使用 `Run()` 和 `EntityManager` 直接操作。不要搬到 hot path
- **PerformanceTests 是有效的规模化参考**：但注意测试条件（entity 数量、feature 组合、chunk packing）是否匹配

## 常见陷阱

1. 照搬入门示例的 `foreach (var (a,b) in SystemAPI.Query<...>())` 到百万 entity 场景
2. 把 DocCodeSamples 中的小规模创建当规模化方案
3. 忽略示例中 `[RequireMatchingQueriesForUpdate]` 的隐藏条件
4. 把 Editor-only API 示例搬到 runtime

## 验收指标

1. Runtime Core 任务能列出至少一个采用或拒绝的 `CASE-*`
2. 不把入门示例中的主线程 foreach、immediate playback 或小规模对象创建当成规模化结论
3. 行动报告包含 CASE 采用/拒绝/暂不相关的明确说明
