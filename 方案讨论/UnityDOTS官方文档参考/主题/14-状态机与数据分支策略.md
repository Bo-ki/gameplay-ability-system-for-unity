# 14 状态机与数据分支策略

## 职责

本主题维护 Unity Entities 官方对 FSM（有限状态机）实现的三种策略、性能权衡和选型决策矩阵。直接映射到 GAS 的 Ability 状态机、ActiveEffect 生命周期状态机、以及 entity 级状态标记。

## 核心概念详解

### 三种实现策略

官方 `state-machine.md` 定义了三种在 ECS 中实现 FSM 的方法：

| 策略 | 机制 | ECS 承载方式 | GAS 适用场景 |
|---|---|---|---|
| **Per-State Data Clustering** | 按状态将 entity 分入不同 archetype | Tag Component / Shared Component | 低频状态切换、状态间数据差异大 |
| **Per-State Data Branching** | 同 archetype 内按状态过滤 | Enableable Component / Job per state | 高频状态开关、大量 idle entity 需要跳过 |
| **Per-FSM Data Branching** | 同 archetype 内单 job 内分支 | enum/bit field in single job | 状态数少、每个状态工作量轻 |

### 策略选择决策树

```
状态切换频率？
  低频（创建/销毁级别）→ Per-State Data Clustering
  高频（每帧可能切换）→ 看 entity 数量
    大量 entity 长期 idle → Per-State Data Branching (Enableable 整 chunk 跳过)
    状态数 ≤ 4 且每状态工作轻 → Per-FSM Data Branching (单 job enum switch)
```

### 官方性能影响矩阵

| 实现问题 | 影响策略 | 监控工具 |
|---|---|---|
| 结构变化 | Per-State Clustering（高频切换时） | CPU Profiler / Structural Changes Profiler |
| 数据碎片化 | Per-State Clustering（状态多、entity 少时） | Archetype Window |
| 不必要的数据获取 | 全部策略（idle entity 多时） | VTune / Instruments cache miss |
| 重复数据获取 | Per-State Branching（多状态时） | VTune / Instruments cache miss |
| Job 开销 | Per-State Clustering + Branching（多状态时） | Profiler job scheduling |
| 复杂依赖 | 全部策略（跨状态访问时） | Profiler job dependencies |
| 触发响应式系统 | Per-State Branching + Per-FSM Branching | Systems Window / Journaling |

## GAS 架构的 FSM 选型映射

### 场景 1：ActiveEffect 生命周期状态

ActiveEffect 状态机：`PendingApply → Active ⇄ Inhibited → PendingRemove → Removed`

**推荐：Per-FSM Data Branching**

理由：
- 状态数少（5 个状态）
- 每个状态的工作量轻（更新 remaining time、period cursor、stack）
- 切换频率中高（Inhibited ↔ Active 每帧可能发生）
- 避免 tag add/remove 产生 archetype churn（直接违反 `SC-01`）

```
BActiveEffectSlot.State: enum { PendingApply, Active, Inhibited, PendingRemove, Removed }
单 job 内 switch(State) { case Active: ... case Inhibited: ... }
```

**禁止：Per-State Clustering via Tag Component**
- 每次 Add/Remove tag = 结构变化 = sync point
- 5 个状态 tag = 最多 32 种 archetype 排列
- 直接违反 `PRF-03` 和 `SC-01`

### 场景 2：Ability 激活状态

Ability 状态：`Idle → Committed → Active → Cooldown → Idle`

**推荐：`AbilityStateComponent.State/Flags` + 可选 `AbilityExecutableTag` skip cache**

理由：
- grant/revoke/cooldown 通常是跨帧状态，首先应有明确 owner-local 权威字段
- ability 是否 executable 是 query 可见性 cache，不是 ability 生命周期本身
- 只有大量 idle ability 被同一 query 高频扫描，且 profiler 证明 skip 收益大于 enableable 同步等待时，才启用 `AbilityExecutableTag`

```
AbilityStateComponent.State/Flags  // authoritative ability runtime state
AbilityExecutableTag : IEnableableComponent  // optional query skip cache only
```

### 场景 3：棋子的生存状态

AutoChess Unit 状态：`Alive / Dead`

**推荐：`TagMaskComponent` / status flags + Structural Commit；可选 `AliveTag` skip cache**

理由：
- Alive/Dead 是 gameplay 权威状态，先进入 tag mask 或状态字段
- 死亡带来的 destroy、cleanup、grant/remove 等结构变化统一进 `GASStructuralCommitSystemGroup`
- `AliveTag` 只在大量 dead entity 仍被 hot query 扫描时作为派生 skip cache

```
TagMaskComponent.Has(DeadTag)
AliveTag : IEnableableComponent  // optional query skip cache only
```

### 场景 4：Buff/Debuff Tag 聚合

多个独立 buff/debuff 标记（如：眩晕、沉默、缴械、减速、灼烧...）

**推荐：Owner-local bit field (Per-FSM Data Branching 变体)**

理由：
- 每个 buff 用独立 tag component 会导致 archetype 爆炸（N 个 tag = 2^N archetype）
- Enableable component 同理，每个 buff 一个 enableable 仍然过多
- bit field 在一个 IComponentData 内枚举所有状态，无 archetype 影响

```
struct CStatusFlags : IComponentData {
    bool Stunned;
    bool Silenced;
    bool Disarmed;
    bool Slowed;
    bool Burning;
    // ...
}
// 单 job 内 if (flags.Stunned) { ... }
```

此模式也满足 `PRF-03`（禁止 Tag Component 做高频状态标记）。

## 多 FSM 叠加问题

当同一 entity 上存在多个 FSM 时（如：既有 Ability 状态机又有 Buff 状态机），官方警告：
- 状态可能不互斥 → 数据碎片化加剧
- 重复数据获取成本上升
- 建议考虑拆分 entity

GAS 应对方针：
- ASC entity 只承载少量核心 FSM（ActiveEffect life cycle、Ability commit）
- 大量临时状态标记（buff/debuff）统一用 bit field 表达
- 拆分的 entity 通过 owner reference 关联

## EX-GAS 项目解读

### 当前 GAS 状态机的对应关系

| GAS 状态机 | 当前表达 | 推荐目标态 | 理由 |
|---|---|---|---|
| ActiveEffect 生命周期 (5 states) | `BActiveEffectSlot.State` enum | 保持 enum + 单 job switch | 已是最佳实践 |
| Ability 激活/冷却 | 独立 component + manual tracking | `AbilityStateComponent.State/Flags`；`AbilityExecutableTag` 仅作可选 query skip cache | grant/revoke/cooldown 多为跨帧状态，不应默认用 enableable 替代所有生命周期；只有大量 idle ability 被同一 query 高频扫描时才值得 skip |
| Unit Alive/Dead | 未统一 | 业务权威进 `TagMaskComponent` / status flags；死亡结构变化进 Structural Commit；可选 `AliveTag` 需 profiler 证明 | alive/dead 常驱动多条业务链，先保证权威状态和结构变化边界，再评估 query skip |
| Status Effect 标记 | 各自独立 component | bit field in `CStatusFlags` | 避免 archetype 爆炸 |
| Tag granted by effect | 各自独立 tag | `TagMaskComponent` / `TagStatusFlagsComponent`；少数高频 query tag 才评估 enableable 或 Chunk Component | tag 权威应是 dense mask，不能把每个 tag 变成 component type |

### 05-ActiveEffectStoreSpec 的一致性验证

`05-ActiveEffectStoreSpec` 第 59 行的选型顺序与本主题一致：

> 状态机选择顺序：enableable 适合高频开关；enum / bit field 适合状态多且同 job 轻分支；tag / archetype 只适合低频且数据差异大的生命周期阶段。

## 常见陷阱

1. **为每个状态创建独立 system**：5 个状态 = 5 个 system × 3 种固定开销。不如单 job 内 switch。
2. **用 Tag Component 做状态标记**：同一次战斗中 entity 状态切换 10 次 = 10 次 archetype 迁移。enableable 不产生迁移。
3. **Enableable 查询成本被忽略**：enableable 过滤仍需要 sync point。如果所有 entity 都是 enabled，不需要 enableable——去掉它反而更快。
4. **盲目使用 Enableable 替代 Add/Remove**：如果状态切换是低频且数据差异极大（如：prefab 实例化前后的 component 集合完全不同），Add/Remove 可能更合适。

## 验收指标

1. GAS Runtime Core 中高频（> 1次/帧）状态切换不使用 Tag Component add/remove
2. ActiveEffect 生命周期保持 enum + 单 job 模式
3. Status Effect 类标记（> 3 种）合并为 bit field 或 enum
4. 大量 idle entity 的场景在 profiler 证明后才使用 Enableable / Chunk Component 整 chunk 跳过
5. Debugger 输出 archetype count 和 enableable wait time
