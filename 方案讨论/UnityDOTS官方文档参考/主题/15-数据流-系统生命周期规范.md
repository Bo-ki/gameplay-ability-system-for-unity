# 15 数据流与系统生命周期规范

## 职责

本主题维护 P2 注意级（设计时参考）规范：数据流确定性、Allocator 归属、数学随机状态、System 生命周期管理。这些是在设计系统架构时需要遵守的规范，不直接影响 hot path 帧时间。

**P0/P1 致命/严重级规范（hot path 必须遵守）见 [13-DOTS编写规范与性能陷阱](13-DOTS编写规范与性能陷阱.md)。**

## 严重度定义

P2-注意：违反在当前规模下可控，但 scale 时会恶化为 P1。frame time 占比 < 5%。达到重选型触发阈值前修复。

## Part D: 数据流与确定性

### P2-01: 确定性输出不得依赖无序写入

**规则：** 影响 battle hash / replay 的结果不得使用无序 `ParallelWriter` 或未排序的 foreach chunk 顺序。并行 fan-in 后必须按确定键排序 merge。

**适用 EX-GAS 模块：** EffectCommand fan-in、TypedFact projection、AttributeDelta reduce

---

### P2-02: NativeContainer 必须明确 Allocator 归属

**规则：** 每个 `NativeList`/`NativeHashMap`/`NativeStream` 等容器必须有明确的 allocator 类型、owner system/entity、dispose/rewind 位置、生命周期边界。

| Allocator | 生命周期 | 适用 |
|---|---|---|
| `Temp` | 一帧内（最多 4 帧安全边际） | 本帧 scratch |
| `TempJob` | Job 内（需手动 Dispose，泄漏检测 4 帧） | job 内临时数据 |
| `Persistent` | 任意长 | 跨帧存储，必须明确 teardown owner |

---

### P2-03: Mathematics.Random 状态必须显式归属

**规则：** Runtime Core 不得使用 `UnityEngine.Random`。`Unity.Mathematics.Random` 的 state 必须明确 owner（system/entity/battle/frame）。

**理由：** `UnityEngine.Random` 是全局非确定性状态。`Mathematics.Random` 是无状态纯函数输入，确定性取决于 seed。

## Part E: System 生命周期

### P2-04: 使用 CreateAfter 确保 System 创建顺序

**规则：** 当 System A 的 `OnCreate` 依赖 System B 创建的 singleton 或资源时，必须用 `[CreateAfter(typeof(SystemB))]`。

**来自官方文档：**
> `systems-update-order.html`: "If you must refer to another system in your OnCreate method, you should use CreateAfter to ensure that your system is created after the other system"

---

### P2-05: ISystem 优于 SystemBase（Burst 编译时）

**规则：** Burst 编译的 system 用 `ISystem`（struct）优于 `SystemBase`（class），因为 `ISystem` 的 Burst 开销更低。

**来自官方文档：**
> `systems-optimizing.html`: "If you use the Burst compiler, the overhead is lower on systems created with ISystem, than those created with SystemBase."

---

### P2-06: [RequireMatchingQueriesForUpdate] 的正确使用

**规则：** 仅在 system 大部分时间不运行时使用此属性。始终有 entity 匹配的 system 不需要它——无条件检查比每次 verify 更快。

**来自官方文档：**
> `systems-optimizing.html`: "avoid using the [RequireMatchingQueriesForUpdate] attribute on systems that don't run all or most of the time."

---

### P2-07: ExclusiveEntityTransaction 仅限 Secondary/Streaming World

**规则：** Runtime Core job 内结构变化默认录制 ECB，并在明确 playback phase 合并执行；主线程可在已知同步点使用 `EntityManager` 或 EntityQuery bulk API。`ExclusiveEntityTransaction` 只作为 secondary / streaming World 的窄口批量结构变化工具，不是通用 worker-thread `EntityManager` 替代，也不作为每帧 hot path API。

**来自官方文档：**
> `concepts-safety.md`: "ExclusiveEntityTransaction allows a single worker thread to perform structural changes on a World, which can free up the main thread to perform other work."
> `concepts-safety.md`: "The main motivation for this feature is to allow a secondary / streaming World to safely modify its entities ... It is not intended as a fully general-purpose interface to EntityManager functionality from worker threads."

**为什么注意：**
- `systems-entity-command-buffer-use.md` 的默认 job 结构变化路径是 ECB：job 里记录命令，job 完成后 playback
- `ExclusiveEntityTransaction` 会让目标 World 进入独占结构变化模式；只保证其直接暴露的 API 子集，不能把 `EntityManager` 任意调用搬进 worker job
- 它适用于 loading/streaming 场景（非每帧 hot path），尤其是 secondary World 不应阻塞 default World 主线程工作时
- GAS Runtime Core 的 ability grant/revoke、request entity destroy、cleanup 等结构变化仍归入 `GASStructuralCommitSystemGroup`

**EX-GAS 潜在应用：**
- AutoChess battle 初始化（批量 entity 创建）
- 场景 streaming 中的 ability system entity 创建
- Definition 预加载期的 entity archetype 准备

**检查方法：**
- Runtime Core hot path 中搜索 `ExclusiveEntityTransaction` → 默认标记为设计错误，除非证明目标是 secondary/streaming World
- Loading/streaming 路径中搜索大批量 `EntityManager.CreateEntity` → 评估是否可以隔离到 secondary World 后使用 `ExclusiveEntityTransaction`

### P2-08: IJobChunk 中 Enableable Mask 处理 — 静默处理已禁用 Entity 的 Bug

**规则：** IJobChunk.Execute 的 `useEnabledMask` 和 `chunkEnabledMask` 参数指示当前 chunk 是否需要 enableable 过滤。若 `useEnabledMask == true` 但 job 使用简单 `for (int i = 0; i < chunk.Count; i++)` 循环，会处理已禁用的 entity（静默逻辑错误）。通用模板应二分：`useEnabledMask == false` 走普通 `for` 快路径；`useEnabledMask == true` 使用 `ChunkEntityEnumerator` 或 `EnabledMask`。若 query 设计上确认无 enableable，则用 `Assert.IsFalse(useEnabledMask)` 固化契约。

**来自官方文档：**
> `iterating-data-ijobchunk-implement.md`: query 包含 enableable component 时必须正确处理 `useEnabledMask/chunkEnabledMask`；确定没有 enableable component 时可用普通 `for` 循环并添加 `Assert.IsFalse(useEnabledMask)`。

**为什么注意：**
- 当前 scale 下可工作，但引入 enableable component 后静默损坏
- 没有编译错误或运行时异常——禁用的 entity 被当作正常 entity 处理
- 在 GAS 中表现为：停用的 effect 仍在计算、已死的 unit 仍在移动

**正确做法：**
```csharp
// 通用模板：无 enableable mask 时走 for 快路径，有 mask 时才用 ChunkEntityEnumerator
public void Execute(in ArchetypeChunk chunk, int unfilteredChunkIndex, 
    bool useEnabledMask, in v128 chunkEnabledMask)
{
    var data = chunk.GetNativeArray(ref MyTypeHandle);

    if (!useEnabledMask)
    {
        for (var i = 0; i < chunk.Count; i++)
            data[i] = ...;
        return;
    }

    var enumerator = new ChunkEntityEnumerator(true, chunkEnabledMask, chunk.Count);
    while (enumerator.NextEntityIndex(out var i))
    {
        // 只处理 enabled entity
        data[i] = ...;
    }
}

// query 设计上确认无 enableable component 时 —— 断言 + 简单循环
public void Execute(in ArchetypeChunk chunk, int unfilteredChunkIndex, 
    bool useEnabledMask, in v128 chunkEnabledMask)
{
    Assert.IsFalse(useEnabledMask);
    var data = chunk.GetNativeArray(ref MyTypeHandle);
    for (int i = 0; i < chunk.Count; i++)
    {
        data[i] = ...;
    }
}
```

**检查方法：**
- Grep IJobChunk.Execute 实现：无 `ChunkEntityEnumerator` / `EnabledMask` 且无 `Assert.IsFalse(useEnabledMask)` 或 `if (!useEnabledMask)` 分支 → 标记为潜在 bug

### P2-09: 每个并行 Job 使用独立 ECB

**规则：** 多个并行 job（IJobEntity/IJobChunk）各自使用独立的 `EntityCommandBuffer` 实例，禁止多个 job 复用同一 ECB。若复用，当 job 使用相同 sortKey 域（如均为 `[ChunkIndexInQuery]`）时，命令会交错而非依序排列。

**来自官方文档：**
> `systems-entity-command-buffers.md`: "It's best practice to use a separate ECB for each distinct job. This is because if you reuse an ECB in consecutive jobs, the jobs might use an overlapping set of sort keys (such as if both use ChunkIndexInQuery), and the commands that the jobs record might be interleaved."

**为什么注意：**
- 不会产生异常或安全错误——静默的交错排序
- 确定性回放 `CASE-35` 在复用 ECB 时被破坏
- 不同 job 记录的 ECB 命令应独立回放

**正确做法：**
```csharp
// 错误：两个 job 复用同一个 ECB
var ecb = ecbSystem.CreateCommandBuffer(state.WorldUnmanaged);
// ... Job1 records: ecb.AddComponent(sortKey, entity, ...)
// ... Job2 records: ecb.RemoveComponent(sortKey, entity, ...)
// Job1 和 Job2 的命令交错混合在同一个 ECB

// 正确：每个 job 独立 ECB
var ecb1 = ecbSystem.CreateCommandBuffer(state.WorldUnmanaged);
var ecb2 = ecbSystem.CreateCommandBuffer(state.WorldUnmanaged);
// Job1 uses ecb1, Job2 uses ecb2 — 各自独立回放，不会交错
```

**检查方法：**
- 审计 `ISystem.OnUpdate` 中 `CreateCommandBuffer` 调用次数与并行 job 数量的对应关系

### P2-10: 读写数据分离到不同 Component 避免响应式系统误触发

**规则：** 遍历组件数据时若声明 read/write 访问（即使未实际修改），Unity 将整个 chunk 标记为已变更，触发所有监听该 component type 的响应式系统（使用 change filter 的系统）。应将只读字段和读写字段分离到不同 component 中。

**来自官方文档：**
> `systems-data-granularity.md`: "Iterating component data with read/write access marks the iterated chunks and all their entities as changed. This makes the reactive systems run, even if the data wasn't modified. You should separate data that's read-only into different components from data which is read/write to avoid running reactive systems needlessly."

**为什么注意：**
- 静默性能退化：不需要运行的系统被触发，浪费 CPU
- IJobEntity 的 `ref` 参数默认为 write access，即使只读取也标记 chunk 变更
- `CASE-38`（`IJobEntityChunkBeginEnd`）可部分缓解但分离 component 是根本方案

**正确做法：**
```csharp
// 反模式：同 component 混合只读和读写字段
struct CUnitState : IComponentData {
    public float Health;      // 读写
    public float MaxHealth;   // 只读（从不修改但触发响应式系统）
    public int Level;         // 只读
}

// 正确：分离只读配置到独立 component
struct CUnitHealth : IComponentData { public float Value; }
struct CUnitConfig : IComponentData { public float MaxHealth; public int Level; }
// IJobEntity 中: void Execute(ref CUnitHealth health, in CUnitConfig config)
```

**检查方法：**
- 审计 IComponentData 中哪些字段运行时被修改、哪些不变
- 不变字段抽到独立 component；确保 IJobEntity 用 `in` 参数

### P2-11: 禁止手动调用其他数据处理 System 的 Update()

**规则：** 禁止在 `ISystem.OnUpdate()` 中手动调用另一个数据处理 system 的 `Update()` 方法。若两个 system 都处理 entity 数据（尤其使用 `SetChangedVersionFilter` 时），调用方 EntityQuery 会看到被调用方处理产生的错误变更版本号。

**来自官方文档：**
> `systems-version-numbers.md`: "If a system manually calls another system's Update() method from inside its own OnUpdate() method, EntityQuery objects in the caller system might see unexpected and incorrect change version numbers based on the processing performed in the target system."

**为什么注意：**
- 变更版本号被破坏 → `SetChangedVersionFilter` 失效 → 响应式系统漏触发或误触发
- 编译器不报错，运行时静默产生错误行为
- 在 GAS 中表现为：effect 重评估遗漏变更、attribute 变更事件丢失、reactive system 不触发

**正确做法：**
```csharp
// 错误：手动调用其他数据处理 system 的 Update()
protected override void OnUpdate()
{
    otherSystem.Update();  // 破坏当前 system 的 EntityQuery 版本号！
    var job = new MyJob { }.Schedule(query, Dependency);
}

// 正确：复用逻辑抽取为 static 方法或 job struct
protected override void OnUpdate()
{
    // 方案 A：抽取公共 job struct 在两个 system 中分别调度
    var handle1 = new SharedJob { }.ScheduleParallel(query, Dependency);
    // 方案 B：通过 SystemGroup 排序确保执行顺序
    var handle2 = new MyJob { }.Schedule(query, handle1);
    Dependency = handle2;
}
```

**检查方法：**
- Grep `\.Update()` 调用在 `OnUpdate()` 方法内部；确认被调用方是否处理 entity 数据

### P2-12: 禁止直接修改 Child / PreviousParent — 由 ParentSystem 管理

**规则：** `Child`（`DynamicBuffer<Child>`）和 `PreviousParent` component 始终由 `ParentSystem` 内部管理。应用代码禁止直接添加、移除或修改这两个组件的值。修改层级关系只能通过设置 `Parent` component 的值完成。

**来自官方文档：**
> `transforms-using.md`: "The `Child` and `PreviousParent` components are always managed by the `ParentSystem`. Application code should never directly add, remove, or change the values of these components."

**为什么注意：**
1. 直接修改 `Child` buffer → `ParentSystem` 下次更新时覆盖为正确值 → 你的修改被静默丢弃
2. 修改 `Parent` component 后，到下一次 `ParentSystem` 更新前层级关系处于不一致状态
3. 手动操作可能破坏 `Child`/`PreviousParent` 的内部一致性

**正确做法：**
```csharp
// 错误：直接修改 Child buffer
var children = SystemAPI.GetBuffer<Child>(parentEntity);
children.Add(new Child { Value = childEntity });  // 禁止！

// 正确：通过 Parent component 建立层级
SystemAPI.SetComponent(childEntity, new Parent { Value = parentEntity });
// ParentSystem 在下次更新时自动维护 Child buffer 和 PreviousParent
```

**检查方法：**
- Grep `Buffer<Child>` / `Child>` 的 `Add`/`Remove` 调用；确认不在应用代码中
- Grep `PreviousParent` 的 `SetComponent` / `AddComponent`；确认不在应用代码中

### P2-13: Singleton API 不自动完成 Job 依赖 —— GetSingletonRW 竞态风险

**规则：** `GetSingleton`/`GetSingletonRW`/`TryGetSingleton` 等 singleton API **不会**等待正在运行的 job 完成。这与普通 component API（`GetComponentData`/`SystemAPI.GetComponent`）行为不同——后者会自动等待可能写入的 job 完成。使用 singleton API 前必须手动 `CompleteDependencyBeforeRO`/`CompleteDependencyBeforeRW`。

**来自官方文档：**
> `components-singleton.md`: "Singleton API calls don't ensure that running jobs are completed first. The Jobs Debugger logs an error on invalid access, and you either need to manually complete dependencies with `EntityManager.CompleteDependencyBeforeRO` or `EntityManager.CompleteDependencyBeforeRW`, or you need to restructure the data dependencies."

**为什么注意：**
1. `GetSingletonRW` 返回 component 数据引用——在 job 仍在读写时通过引用修改数据 = 竞态条件
2. Jobs Debugger 会报错但仅在开发模式有效；发布版本为静默竞态
3. `GetSingletonRW` 最佳实践：仅用于访问 NativeContainer（NativeContainer 有独立安全机制）；否则检查 Jobs Debugger 错误

**正确做法：**
```csharp
// 危险：GetSingletonRW 不等待 job 完成
var config = SystemAPI.GetSingletonRW<CConfig>();  // 返回 RefRW
config.ValueRW.someField = newValue;  // 若有 job 正在读 CConfig → 竞态！

// 安全方案 A：手动完成依赖
state.EntityManager.CompleteDependencyBeforeRW<CConfig>();
var config = SystemAPI.GetSingletonRW<CConfig>();

// 安全方案 B：将 mutable 数据放在 NativeContainer 中
// NativeContainer 有自己的 safety handle，与 ECS safety 独立
struct CConfig : IComponentData {
    public NativeList<int> Data;  // NativeContainer 安全
}
var config = SystemAPI.GetSingletonRW<CConfig>();
config.ValueRW.Data.Add(42);  // NativeContainer safety 保护
```

**检查方法：**
- 搜索 `GetSingletonRW` 调用：确认是否在 job 调度之后、有未完成 job 依赖时访问
- 检查返回的 RefRW 是否通过引用修改数据，且无 `CompleteDependencyBeforeRW`
- 若无 NativeContainer 包装且无 CompleteDependency → 标记为潜在竞态

## 检查清单

### Allocator 与确定性

- [ ] NativeContainer allocator 类型明确
- [ ] Persistent 容器有 owner 和 teardown 路径
- [ ] 确定性输出使用确定性 merge 策略
- [ ] Mathematics.Random state 显式归属
- [ ] `ExclusiveEntityTransaction` 仅出现在 secondary/streaming World 路径；Runtime Core hot path 结构变化仍走 ECB / bulk query（P2-07）
- [ ] IJobChunk 中 enableable mask 处理正确：`useEnabledMask == false` 走 for 快路径或 assert；`useEnabledMask == true` 用 `ChunkEntityEnumerator` / `EnabledMask`（P2-08）
- [ ] 批量添加/移除多个 component 用 `ComponentTypeSet` 一次完成（CASE-33）

### ECB 与 Job

- [ ] 每个并行 Job 使用独立 ECB 实例（PRF-25 / P2-09）
- [ ] 读写数据分离到不同 component：只读字段与读写字段不在同一 component 中（PRF-26 / P2-10）
- [ ] 无手动调用其他数据处理 System 的 Update()（PRF-27 / P2-11）
- [ ] 无直接修改 `Child`/`PreviousParent` 组件（PRF-28 / P2-12）
- [ ] Singleton API 调用前手动完成依赖或改用 NativeContainer 包装（PRF-29 / P2-13）
- [ ] `SystemAPI.Query` 中 `DynamicBuffer<T>` 默认可读写：只读场景需自定义实现避免不必要 sync point（PRF-30）
- [ ] ECS Child Buffer 迭代顺序不确定：禁止依赖 sibling index 做确定性排序（PRF-31）
- [ ] 主线程数据操作禁用 `.Run()` Job：主线程 `SystemAPI.Query` foreach 无 job dep system 开销，`.Run()` 有（PRF-32）
- [ ] EntityQuery 必须通过 `SystemState.GetEntityQuery` 创建：禁止 `EntityManager.CreateEntityQuery`（PRF-33）
- [ ] NativeContainer 放在 IComponentData 上时禁止对该 component 调度 IJobChunk/IJobEntity（PRF-34）
- [ ] NativeArray/NativeList/NativeStream 跨 Job 传递时手动串联 JobHandle；ECS Dependency 不会自动追踪 NativeContainer 数据流（`scheduling-jobs-dependencies.md`）
- [ ] `SystemAPI.Query` 不可存为变量复用：必须内联 foreach（CASE-46）
- [ ] 主线程读取单例配置优先 `SystemAPI.GetSingleton<T>()` 而非 `EntityManager.GetComponentData<T>()`（SEL-05）

## 常见陷阱

1. **"IJobChunk 的 for 循环遍历所有 entity 就行"** — 若 query 包含 enableable component 但未使用 `ChunkEntityEnumerator`，会静默处理已禁用的 entity。
2. **"多个 Job 共用一个 ECB 方便"** — 复用 ECB 在多个使用 `[ChunkIndexInQuery]` 的 job 中导致命令交错，破坏确定性回放。每个并行 job 独立 ECB。
3. **"一个大 Component 包含所有属性最方便"** — 读写字段与只读字段共用 component 导致每个写入触发所有监听该 component 的响应式系统，即使只读字段从未变化。
4. **"手动调用其他 System 的 Update() 就能复用逻辑"** — 被调用方的 entity 数据处理会破坏调用方 EntityQuery 的变更版本号，导致响应式系统漏触发或误触发。
5. **"我把这个 entity 加到 parent 的 Child buffer 就行"** — `Child` buffer 由 `ParentSystem` 自动管理，直接修改会被下次 `ParentSystem` 更新覆盖。应通过设置 `Parent` component 建立层级关系。
6. **"GetSingletonRW 在主线程改个配置很方便"** — singleton API 不等待 job 完成。若有 job 正在读写该 component，返回引用后直接修改 → 数据竞态。必须先手动 CompleteDependency 或将 mutable 数据放入 NativeContainer。

---

## 验收指标

1. 所有 Persistent 容器有明确 owner 和 teardown 路径
2. 无手动调用其他数据处理 System 的 Update() 
3. 无直接修改 Child/PreviousParent 的应用代码
4. 每个 GetSingletonRW 调用有明确的依赖完成或 NativeContainer 包装
