# 16 官方案例模式-高级

## 职责

本主题维护 CASE-21 ~ CASE-47，涵盖高级/专项 DOTS 模式：高级 ECB 操作、Chunk 级优化、BlobAsset 构建、自定义 Transform、Baking 高级、Scene Streaming、系统数据模式等。这些模式用于特定场景，不需要在日常开发中频繁查阅。

**日常高频 CASE 模式（CASE-01~20）见 [12-官方案例模式](12-官方案例模式.md)。**

## CASE 规则详解

| 编号 | 模式 | 官方示例特征 | EX-GAS 用法 | 拒绝条件 |
|---|---|---|---|---|
| `CASE-21` | ECB `PlaybackPolicy.MultiPlayback` + Deferred Entity Remapping | `new EntityCommandBuffer(Allocator.TempJob, PlaybackPolicy.MultiPlayback)` + 同一 ECB 内先 `CreateEntity()` 后引用（自动 remapping） | 多 pass 效果应用（同一 ECB 多次 Playback 到不同 World state）；同一 ECB 内创建 entity 并立即通过 placeholder entity 添加 component / set component / append buffer（利用 deferred entity remapping 自动映射到真实 entity）。配合 `[ChunkIndexInQuery] int sortKey` 实现确定性 ECB playback 顺序 | 单次 playback 场景（默认 `SinglePlayback` 更安全） |
| `CASE-22` | `EntityQueryMask` 快速实体匹配 | `query.GetEntityQueryMask()` + `mask.MatchesIgnoreFilter(entity)` | O(1) entity-query 成员检查：无需逐 component 调用 `HasComponent`。GAS 场景：entity 分类过滤、archetype 分组路由、条件系统跳过判断。`MatchesIgnoreFilter` 忽略 enableable / shared component filter | 单次/低频查询（构建 mask 有开销，高频才值得） |
| `CASE-23` | `BufferAccessor<T>` Chunk 级 Buffer 批量访问 | `chunk.GetBufferAccessorRO/RW(ref BufferTypeHandle)` in IJobChunk | IJobChunk 中批量 buffer 操作：替代 per-entity `BufferLookup<T>` 随机访问。提供 chunk 内所有 entity 的 buffer 一次性访问。`BufferTypeHandle<T>` 与 `BufferLookup<T>` 不同，用于 IJobChunk 的 chunk 级访问。GAS 场景：effect store 批量读写、attribute delta 批量收集。可通过 `buffer.Reinterpret<U>()` 重解释元素类型 | IJobEntity 遍历（用 `DynamicBuffer<T>` in Execute 参数更直接） |
| `CASE-24` | `BlobBuilder` 标准构建模式 | `BlobBuilder.ConstructRoot<T>()` + `Allocate(ref blobArray, count)` + `AllocateString(ref blobString, string)` + `SetPointer(ref blobPtr, ref element)` | Definition 层 BlobAsset 构建：GE 定义、Ability 定义等静态数据。`ISystem` 在 `OnCreate` 中通过 `BlobBuilder` 创建 `BlobAssetReference<T>` 并存入 singleton component，`OnDestroy` 中 `Dispose()`。`BlobArray` 通过 `Allocate` 返回的 `BlobBuilderArray` 逐元素初始化 | Runtime 可变状态存储（用 DynamicBuffer） |
| `CASE-25` | `IECBSingleton` 自定义 ECB System | 继承 `EntityCommandBufferSystem` + 实现 `IECBSingleton` + `RegisterSingleton<Singleton>` | 自定义 ECB phase：除默认 Begin/End Simulation 外，为 `GasStructuralPlaybackSystemGroup` 创建独立 ECB system。通过 singleton entity 暴露 ECB 给 job，`ecbSystem.AddJobHandleForProducer(Dependency)` 注册 job 依赖。GAS 场景：frame backbone 中多个 structural playback phase 各自拥有独立 ECB system | 仅使用默认 Begin/End Sim ECB 够用时 |
| `CASE-26` | `ChunkEntityEnumerator` 标准 Enableable 感知迭代 | `if (!useEnabledMask) for ... else new ChunkEntityEnumerator(true, chunkEnabledMask, chunk.Count)` | IJobChunk 中必须感知 enableable mask。当 `useEnabledMask == true` 时，简单 `for (int i = 0; i < chunk.Count; i++)` 会处理已禁用 entity，必须用 `ChunkEntityEnumerator` 或 `EnabledMask`；当 `useEnabledMask == false` 时，普通 for 是官方允许的快路径。query 设计上确认无 enableable 时用 `Assert.IsFalse(useEnabledMask)` 固化契约 | 在 `useEnabledMask == true` 时使用简单 for 循环 |
| `CASE-27` | `chunk.Has<T>()` Chunk 级可选组件检查 | `chunk.Has<Rotation>() && chunk.Has<LocalToWorld>()` in IJobChunk.Execute | 一次 chunk 级判断替代逐 entity 检查。当 chunk 中所有 entity 共享同一 archetype 时，`chunk.Has<T>` 对整 chunk 返回相同结果。将可选组件处理循环放在 `if (chunk.Has<T>())` 内部，避免 per-entity 分支开销 | 同一 chunk 内 entity 的 component 组合不一致时（不可能，同一 archetype 保证一致） |
| `CASE-28` | Chunk Component 空间分区 / 共享数据 | `chunk.GetChunkComponentData(ref TypeHandle)` / `chunk.SetChunkComponentData(ref TypeHandle, value)` in IJobChunk | 每 chunk 一份的共享数据（如 AABB、visibility flags、LOD level）。查询用 `WithAllChunkComponentRW<T>` / `WithNoneChunkComponent<T>`。配合 `chunk.DidChange` 实现 chunk 级脏标记跳过。GAS 场景：目标获取空间分区、chunk 可见性批处理、effect 范围预判 | 需要 per-entity 粒度的数据（用常规 component 或 enableable） |
| `CASE-29` | Custom Transform via WriteGroup + ManualOverride | `[WriteGroup(typeof(LocalToWorld))]` on custom transform + `TransformUsageFlags.ManualOverride` in Baker | 完全替代标准 transform 系统的自定义 transform。WriteGroup 使标准 `LocalToWorldSystem` 跳过持有自定义 transform 的 entity；`ManualOverride` 阻止 Baker 添加标准 transform component。GAS 场景：2D 网格坐标、固定轴旋转、非标准空间变换 | 仅需微小调整的标准 transform（直接用 `LocalTransform` + `Parent`） |
| `CASE-30` | `CreateAdditionalEntity()` 单 Authoring 多 Entity | `CreateAdditionalEntity(TransformUsageFlags, entityName)` in Baker | 一个 authoring component 产出多个 runtime entity。GAS 场景：一个 AbilityDefinition authoring → ability entity + 多个 GE entity + cue entity | 简单 1:1 映射 |
| `CASE-31` | `DependsOn()` 在 Early-Out 之前 | `DependsOn(authoring.Reference)` 必须在所有 `if (ref == null) return` 之前调用 | 确保外部引用恢复时 Baker 被重新触发。即使引用为 null，`DependsOn` 也建立跟踪依赖 | Baker 无外部依赖时 |
| `CASE-32` | `[TemporaryBakingType]` + Baking System Burst 计算 | Baker 写入 `[TemporaryBakingType]` 临时数据 → `[WorldSystemFilter(BakingSystem)]` + `[BurstCompile]` ISystem 做 Burst 计算 → 写入持久化 component | 复杂数据转换在 Baking System 中用 Burst 完成，Baker 只做轻量数据搬运。Temporary 数据在当前 bake pass 结束后自动清除 | Baker 中计算足够快（< 1ms） |
| `CASE-33` | `ComponentTypeSet` 批量组件添加/移除 | `new ComponentTypeSet(typeof(A), typeof(B))` + `EntityManager.AddComponent(entity, typeSet)` | 一次结构变化添加/移除多个组件，最小化 archetype 中间态。避免逐 component 添加产生冗余 archetype | 单个 component 操作 |
| `CASE-34` | `EntityQueryCaptureMode.AtPlayback` ECB 延迟 Query 评估 | `ecb.AddComponent(query, new C(), EntityQueryCaptureMode.AtPlayback)` | ECB 记录时存储 query，playback 时评估 → 批量 chunk 级结构变化（1M entity: 3.5ms vs NativeArray 35ms vs IJobEntity ECB 170ms） | 即时模式（默认，entity 数量少时差异不大） |
| `CASE-35` | `[ChunkIndexInQuery] int sortKey` 确定性 ECB 回放 | `ecb.AddComponent(sortKey, entity, new C())` — 并行 job 中 sortKey 作为 ECB 方法第一个参数 | 并行 job 录制顺序不确定但回放顺序确定：每个 ECB 方法第一个参数传递 `[ChunkIndexInQuery]` 作为 int sortKey；回放前按 sortKey 排序，sortKey 大者后执行。sortKey 与 job 调度无关时 → 确定性回放。GAS 场景：多 effect 并行评估的 ECB 写入、require deterministic replay/debug | 不需要确定性时（sortKey 有微开销，省略可提升录制速度） |
| `CASE-36` | `DynamicBuffer.Reinterpret<U>()` 同大小类型重解释 | `myBuffer.Reinterpret<int>()` — 同 sizeof 的不同类型 aliased 到同一块内存 | 将 `DynamicBuffer<T>` 重解释为 `DynamicBuffer<U>`（sizeof(T)==sizeof(U)），共享同一块内存和安全句柄。修改 `intBuffer[i]` 等价于修改 `myBuffer[i]` 的对应字节。GAS 场景：reinterpret `DynamicBuffer<EffectSpec>` → `DynamicBuffer<Entity>` 提取 entity 字段、reinterpret int buffer → float buffer 批量转换 | 跨大小类型（sizeof(T)!=sizeof(U) 编译失败）；语义不合理时（如 float→int 位模式被误解） |
| `CASE-37` | `LinkedEntityGroup` 批量生命周期管理 | root entity 持有 `DynamicBuffer<LinkedEntityGroup>`，`DestroyEntity(root)` → 所有 linked entity 自动销毁 | Instantiate/Destroy/SetEnabled 操作根 entity 自动递归到 buffer 中所有 entity。第一个元素必须是根 entity 自身。不与 transform hierarchy 递归（独立概念）。不可嵌套（LinkedEntityGroup A 不包含 B 的内容）。GAS 场景：ASC entity + granted ability/effect entity 统一生命周期（销毁 ASC → 自动清理所有关联 entity） | 独立生命周期 entity（需单独管理）；部分 linked entity 需要不同 SceneTag 时 |
| `CASE-38` | `IJobEntityChunkBeginEnd` Chunk 级预评估跳过 | 在 IJobEntity 中实现 `OnChunkBegin(in ArchetypeChunk chunk, ...)` + `OnChunkEnd(...)` | 在获取组件写访问前对 chunk 做预评估（如 AABB 检测、LOD 判断），可提前 `return false` 跳过整个 chunk。跳过的 chunk 不获取 write access → 不增加版本号 → 不触发响应式系统。GAS 场景：effect 重评估跳过未变更 chunk、LOD 距离剔除、visibility culling | 简单 per-entity 操作无需此粒度控制；IJobChunk 已提供等价 chunk 级控制 |
| `CASE-39` | Baker 只添加不读取 — Baker 间无依赖 | Baker 内 `GetComponent<T>()` / `SetComponent<T>()` 不可用；只能 `AddComponent<T>()` | Baker 之间无依赖关系：Baker 只能向当前 entity **添加**新 component，不能读取已有 component 的值，也不能访问/修改其他 entity。需要读取已有数据做复杂计算时，在 Baking System（`[WorldSystemFilter(BakingSystem)]` + `[BurstCompile]` ISystem）中用 Burst 完成（参考 `CASE-32`）。若在 Baker 中访问其他 entity 会导致未定义行为。GAS 场景：Ability/GE/Buff definition 的 Baker 只负责烘焙期数据搬运；GE 的 modifier 计算逻辑放在 Baking System | 简单 1:1 属性映射（Baker 直接 `AddComponent` 即可） |
| `CASE-40` | Baker 必须无状态 — 禁止在 Baker 实例中缓存数据 | Baker 只实例化一次，`Bake()` 被多次调用且顺序不确定；不能在字段中缓存状态 | Baker 是单例实例（每个 Baker 类型一个实例），其 `Bake()` 方法在非确定性顺序下被多次调用（增量烘焙跨长时间运行）。在 Baker 字段中缓存任何值违反不变式，导致烘焙行为异常。所有数据访问必须通过 Baker 方法（自动记录依赖和产出以支持增量烘焙的 undo/redo）。GAS 场景：GE/Ability definition Baker 的 `Bake()` 方法必须无状态，定义数据通过 `BlobBuilder` 或 component 产出 | 通过 Baker 方法访问的数据（自动追踪依赖） |
| `CASE-41` | Baking System 必须手动追踪依赖和增量还原 | Baking System 不自动追踪依赖和结构变化；需显式 `DependsOn()` 并在添加组件时手动追踪/撤销变更 | Baking System 与 Baker 不同，不会自动记录依赖或产出。必须：1) 对所有外部数据引用显式调用 `DependsOn()`；2) 当向 entity 添加 component 时手动追踪并实现撤销逻辑以支持增量烘焙。Baking System 中创建的 entity **不会**出现在 baked entity scene 中（仅用于系统间数据传递）；要输出到 scene 的 entity 必须在 Baker 中通过 `CreateAdditionalEntity` 创建。GAS 场景：批量 GE 属性计算、Definition 数据关联与过滤 | Baker 中计算足够快（Baker 自动追踪依赖） |
| `CASE-42` | Scene Section 跨引用限制 — Entity 引用只能同 Section 或 Section 0 | ECS component 中 `Entity` 字段只能引用同 section 或 section 0 的 entity | SubScene 中 ECS component 的 entity 引用有严格限制：**只能引用同一 section 内的 entity，或 section 0 中的 entity**。引用其他 section 的 entity 在加载时被静默设为 `Entity.Null`。GAS 场景：若 Ability entity（section 1）需要引用目标 ASC entity（section 2），必须将 ASC entity 放入 section 0，或将两者放在同一 section。同时注意 prefab 实例继承 `SceneSection` component——卸载该 section 的场景时所有关联 prefab 实例被销毁；若需持久化需手动移除 `SceneSection` | 非 SubScene 模式（纯运行时创建的 entity 无 SceneSection 限制） |
| `CASE-43` | PostLoadCommandBuffer + ProcessAfterLoadGroup 场景实例化自定义 | `PostLoadCommandBuffer` managed component（包含 ECB）+ `ProcessAfterLoadGroup` system group（在 streaming world 中运行） | 场景加载不在 main world 而在独立的 streaming world 进行。加载完成后 `ProcessAfterLoadGroup` 在 streaming world 中运行（所有内容已加载但尚未移入 main world），允许对场景实例进行 per-instance 修改（偏移、配置注入等）。`PostLoadCommandBuffer` 是一种 managed component（含 ECB），section 加载时 streaming system 检查其存在并在 `ProcessAfterLoadGroup` 之前执行。GAS 场景：AutoChess 需要从同一场景文件创建多个战斗实例，每个实例不同初始位置、不同队伍配置——通过 `SceneLoadFlags.NewInstance` + `PostLoadCommandBuffer`（创建 per-instance 配置 entity）+ `ProcessAfterLoadGroup`（读取配置并应用偏移）实现，避免为每个实例 bake 独立场景 | 所有实例完全相同的简单复制（无需 per-instance customization） |
| `CASE-44` | Custom Section Metadata — 烘焙阶段向 Section Meta Entity 附加自定义元数据 | `SerializeUtility.GetSceneSectionEntity` 在 Baking System 中获取 section meta entity，添加组件作为自定义元数据 | Section meta entity 在场景内容加载**之前**就已可用。可在 Baking System（非 Baker）中通过 `SerializeUtility.GetSceneSectionEntity` 获取 section meta entity 并附加自定义 ECS component 作为元数据（如包围盒、PVS 信息、加载条件）。这些 metadata 可在运行时通过 `ResolvedSectionEntity` buffer 从 scene meta entity 查询各 section meta entity 获取。GAS 场景：AutoChess 大战场场景按空间分区 section 流式加载——可在 meta entity 上存储 section 包围盒和触发条件，运行时根据玩家/摄像机位置决定加载/卸载 section，实现智能流式管理 | 所有 section 无条件立即加载的简单场景 |
| `CASE-45` | System-Associated Entity Data — 系统级数据存为组件而非系统字段 | `SystemAPI.SetComponent(state.SystemHandle, data)` + `SystemAPI.GetComponent<T>(state.SystemHandle)` 在系统关联 entity 上存取数据 | 官方推荐使用 ECS component 存储系统级公开数据，而非将数据定义为 system struct 的字段。使用 `SystemHandle` + `SystemAPI.SetComponent/GetComponent` 将数据附加到系统关联 entity，数据生命周期自动跟随系统（系统销毁时 entity 自动清理）。好处：1) 其他系统可通过正常 ECS query 访问数据，无需持有系统引用；2) 线程安全和生命周期安全由 ECS 保证；3) 符合数据导向设计原则。GAS 场景：Frame Backbone 中 SystemGroup 级配置（如 budget/threshold/counters）、Debugger 诊断状态——都应存为 component 而非 system 字段 | 仅在当前 system 内部使用的临时状态（不需要被其他 system 访问） |
| `CASE-46` | `SystemAPI.Query` 不可存储复用 — 必须内联 foreach | `foreach (var (a, b) in SystemAPI.Query<A, B>())` 必须直接写在 foreach 语句中 | `SystemAPI.Query<T>` 依赖编译时 source generator 确定类型参数，生成缓存 `EntityQuery`、type handle update 和依赖完成代码。无法将 query 存为变量后在多个 `foreach` 中复用——source gen 在编译时无法确定运行时变量的类型。GAS 场景：同一 query 需多处使用时，创建独立 `EntityQuery` 字段通过 `SystemAPI.GetEntityQuery<T>()` 缓存后手动迭代 | 单次 foreach 使用（正常场景）；需要复用时改用 `EntityQuery` + `IJobChunk`/`IJobEntity` |
| `CASE-47` | ECB `AppendToBuffer` + `sortKey` 多源并行 fan-in | `EntityCommandBuffer.AppendToBuffer<T>(sortKey, entity, element)` 追加元素保留已有内容 | 多个并行 job 通过 ECB 向同一 entity 的同一 buffer 追加元素时，`sortKey` 决定元素最终顺序。`AppendToBuffer` 保留已有 content（累加），`SetBuffer` 覆盖整个 buffer（最后 sortKey 获胜）。**必须**在 `AppendToBuffer` 之前 `AddComponent<T>` 确保 buffer component 存在（buffer 不存在时 `AppendToBuffer` 在 playback 失败）。GAS 场景：EffectCommand fan-in — 多个 Attribute/GE/Tag system 通过 ECB 向同一 ASC entity 的 outbox buffer 追加输出命令，各 system 独立 job 并行录制，sortKey 保证确定性合并顺序 | 单源写入或需要完全替换 buffer 内容时用 `SetBuffer`（覆盖）；不需要多源 fan-in 时 |

## 常见陷阱

1. 把高级模式当成默认选择——大部分场景 CASE-01~20 已足够，高级模式增加复杂度
2. Baker 中违反"只添加不读取"原则——Baker 间无依赖，读取已有 component 导致未定义行为
3. Scene Section 跨引用在加载时静默变为 Entity.Null——无编译/运行时警告
4. Baking System 中创建的 entity 不会出现在 baked scene——忘记此限制导致 entity 丢失
